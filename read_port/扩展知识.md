## 1. Python GIL（全局解释器锁）

### 1.1 GIL 是什么？为什么存在？

GIL（Global Interpreter Lock）是 CPython 解释器的一把全局锁，**同一时刻只允许一个线程执行 Python 字节码**。

它保护的是 Python 的引用计数垃圾回收机制：

```python
a = []        # 列表对象，引用计数 = 1
b = a         # 引用计数 = 2
del b         # 引用计数 = 1
del a         # 引用计数 = 0 → Python 自动回收内存
```

如果没有 GIL，两个线程同时操作同一个对象：

```
线程 A: 读引用计数 = 1
线程 B: 读引用计数 = 1        ← 同时读到旧值！
线程 A: 计数 + 1 = 2，写回
线程 B: 计数 + 1 = 2，写回    ← 应该是 3，结果写了 2

引用计数错了 → 对象被提前回收 → 访问已释放的内存 → segfault 崩溃
```

GIL 的解法很粗暴：同一时刻只让一个线程跑，不存在竞争。
代价：8 核 CPU，Python 多线程只能用 1 核。

### 1.2 GIL 对不同场景的影响

```
I/O 密集型（Web 服务、数据库查询、网络请求）：
  线程等 I/O 时会释放 GIL → 其他线程可以跑
  async/await 更进一步，连线程都不需要
  → GIL 影响不大

CPU 密集型（图像处理、科学计算、数据分析）：
  线程一直在算，不释放 GIL → 其他线程干等着
  多线程 ≈ 单线程
  → GIL 影响致命
```

**CPU 密集型的标准解法**：多进程（multiprocessing / gunicorn workers / Arq Worker）。每个进程有自己的 GIL，互不干扰。

### 1.3 Python 3.14 free-threaded 模式（no-GIL）

**当前最新稳定版：Python 3.14.3**（3.15 在 alpha 阶段）。

| 版本 | 状态 |
|---|---|
| 3.13（2024.10） | 首次引入 free-threaded 模式，实验性 |
| 3.14（2025.10） | **官方正式支持**，安装包自带 free-threaded 二进制文件 |
| 3.15（预计 2026.10） | 预计进一步成熟 |

3.14 的 free-threaded 模式已经不是实验性了，是官方支持的。但仍然是**可选的**——默认安装还是带 GIL，需要专门选择 free-threaded 版本：

```bash
# 验证是否是 free-threaded 版本
python -c "import sys; print(sys.version)"
# 如果包含 "free-threading build" 字样 → 无 GIL

python -c "import sys; print(sys._is_gil_enabled())"
# False → GIL 已禁用
```

**生态适配现状**（截至 2026.03）：

已支持 free-threaded：
- NumPy (2.1.0+)、SciPy (1.15.0+)、pandas (2.2.3+)
- PyTorch (2.6.0+)、JAX (0.5.1+)
- Pillow (11.0.0+)、matplotlib (3.9.0+)
- pydantic (2.11.0+)、cryptography (46.0.0+)
- scikit-learn (1.6.0+)

仍在适配中：lxml、polars、grpcio 等

纯 Python 代码天然兼容，不需要改。需要适配的是 C 扩展库。
如果 import 了未适配的 C 扩展，Python 会**自动重新启用 GIL** 并输出警告。

### 1.4 没了 GIL 性能提升多少？

**取决于场景，不是万能药。**

```
CPU 密集型多线程 → 提升巨大：
  有 GIL：4 个线程轮流用 1 个核 → 和单线程差不多
  无 GIL：4 个线程各占 1 个核 → 接近 4 倍提升

I/O 密集型 → 几乎没提升：
  async 已经解决了 I/O 等待问题，GIL 有没有都一样

单线程 → 反而略慢：
  官方数据：free-threaded 版本单线程有 1~8% 性能开销
  因为去掉 GIL 后，每个对象需要更细粒度的锁保护引用计数
```

**对我们项目的影响**：

```
FastAPI API 服务 → I/O 密集 → async 已经够了 → no-GIL 没帮助
YOLO 推理 → CPU 密集 → 已经用多进程（Arq Worker）解决 → no-GIL 没帮助
```

no-GIL 真正受益的场景：科学计算、数据处理、图像批处理等 CPU 密集型任务，且任务之间需要共享大量内存（多进程共享内存很麻烦，多线程天然共享）。

### 1.5 多进程会被淘汰吗？

**不会。** 即使 GIL 完全消失，多进程仍然有不可替代的优势：

1. **故障隔离** — 一个 worker 崩了（OOM、segfault），其他 worker 不受影响。多线程一个线程崩了，整个进程都死
2. **内存保护** — 进程间内存隔离，一个 worker 的内存泄漏不会拖垮其他 worker
3. **部署灵活** — 多进程可以分布到多台机器，多线程只能在一台机器内

生产部署的标准答案仍然是 gunicorn + uvicorn workers。

### 1.6 面试话术

> "GIL 保护 CPython 的引用计数不被多线程竞争破坏，代价是多线程无法真正并行。
> 3.14 开始官方支持 free-threaded 模式，主流科学计算库已经适配。
> 但对 Web 服务影响不大——I/O 密集用 async，CPU 密集用多进程，这两个方案不依赖 GIL 的有无。
> 生产部署仍然用多进程，因为故障隔离和内存保护是多线程替代不了的。"

> 追问"那 no-GIL 有什么用？"：
> "主要受益场景是 CPU 密集型且需要共享大量内存的任务，比如科学计算、数据处理。
> 多进程共享内存很麻烦（需要 shared memory 或序列化），多线程天然共享。
> 去掉 GIL 后多线程能真正并行，这类场景提升巨大。"

## 2. Uvicorn 多进程部署

### 2.1 开发环境 vs 生产环境

```bash
# 开发环境：单进程 + 热重载
uv run uvicorn app.main:app --reload

# 生产环境方式 1：uvicorn 自带多 worker
uvicorn app.main:app --workers 4 --host 0.0.0.0 --port 8000

# 生产环境方式 2：gunicorn 做进程管理器（更常见）
gunicorn app.main:app -w 4 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:8000
```

`--workers 4` 启动 4 个独立进程，每个进程是一个完整的 FastAPI 应用。

### 2.2 为什么要多进程？

Python 的 GIL 限制了单进程的 CPU 并发。async 只解决 I/O 等待（等数据库、等网络），CPU 密集型操作还是被 GIL 卡住。多进程让每个 worker 独占一个核。

### 2.3 多进程的内存模型

**每个 worker 是 fork 出来的独立进程，内存完全隔离**：

```
┌──────────────────────────────────────────┐
│                 操作系统                   │
│                                          │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │ worker 1 │ │ worker 2 │ │ worker 3 │ │
│  │counter=3 │ │counter=1 │ │counter=2 │ │
│  │ 自己的内存 │ │ 自己的内存 │ │ 自己的内存 │ │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ │
│       └────────────┼────────────┘        │
│                    ▼                     │
│            ┌──────────────┐              │
│            │    Redis     │ ← 独立进程    │
│            │  counter = 6 │ ← 所有人共享  │
│            └──────────────┘              │
└──────────────────────────────────────────┘
```

worker 1 的 `counter = 3` 和 worker 2 的 `counter = 1` 是两个完全不同的变量，互相看不见。

**这就是为什么限流、缓存、会话等共享状态必须放 Redis，不能放 Python 变量。**

### 2.4 面试话术

> "生产环境用 gunicorn + uvicorn worker 多进程部署。每个 worker 是独立进程，
> 内存不共享，所以限流计数器、缓存、会话等共享状态必须放 Redis。
> Python 的 GIL 限制了单进程的 CPU 并发，多进程是标准解法。"

> **面试红线**：如果你说"我用 `uvicorn --reload` 跑的"，面试官会直接判断你没部署过生产。

## 3. Redis Sorted Set（有序集合）

> 在 Day 9 的 7.2 滑动窗口限流中用到，这里补充基础语法。

### 3.1 是什么？

Sorted Set = 每个元素带一个分数（score），Redis 自动按分数从小到大排序。

对比你已经学过的数据结构：

| 类型 | 用过的场景 | 特点 |
|---|---|---|
| String | `SET task:result:1 "{...}"` | 一个 key 对应一个值 |
| List | Arq 任务队列（RPUSH/BLPOP） | 有序，可重复 |
| **Sorted Set** | 滑动窗口限流 | 每个元素带分数，按分数自动排序 |

### 3.2 基础命令

```redis
# ===== ZADD：添加元素（带分数） =====
ZADD myset 100 "alice"
ZADD myset 85  "bob"
ZADD myset 92  "charlie"
# 集合内部自动排序：bob(85) < charlie(92) < alice(100)

# ===== ZRANGE：按排名查看 =====
ZRANGE myset 0 -1 WITHSCORES
# → bob(85), charlie(92), alice(100)
# 0 -1 表示从第 0 个到最后一个（全部）

# ===== ZCARD：数元素个数 =====
ZCARD myset
# → 3

# ===== ZRANGEBYSCORE：按分数范围查 =====
ZRANGEBYSCORE myset 80 95 WITHSCORES
# → bob(85), charlie(92)
# alice(100) 不在 80~95 范围内

# ===== ZREMRANGEBYSCORE：按分数范围删除 =====
ZREMRANGEBYSCORE myset 0 89
# → 删了 1 个（bob: 85）
# 集合剩：charlie(92), alice(100)
```

### 3.3 命令速查

| 命令 | 作用 | 时间复杂度 |
|---|---|---|
| `ZADD key score member` | 添加元素（带分数） | O(log N) |
| `ZCARD key` | 返回元素个数 | O(1) |
| `ZRANGE key start stop` | 按排名范围查 | O(log N + M) |
| `ZRANGEBYSCORE key min max` | 按分数范围查 | O(log N + M) |
| `ZREMRANGEBYSCORE key min max` | 按分数范围删 | O(log N + M) |

### 3.4 实战应用：滑动窗口限流

核心思路：把每次请求的时间戳当作 score，数"最近 60 秒内有几条"。

详细原理和代码见 Day 9 教程 Step 7.2 的"深入理解：滑动窗口限流"部分。
