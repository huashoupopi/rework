## 二、批次 2:后端安全必修

> 来源:2026-08-17 全盘代码审查,问题已人工抽查;修法经外部审查修订为**唯一选定方案**(不给执行 AI 留二选一)。每件修复配一个「修复前会失败」的回归测试。

### 2.1 `/static` 无鉴权(IDOR,最高优先)——修法已选定:鉴权接口

- **现状**:`backend/app/main.py:72` 直接挂载 StaticFiles,上传原图/检测结果图/聊天图猜到路径即可匿名下载。且 `<img src="/static/...">` 无法携带 localStorage 里的 Bearer token,**签名 URL 方案不采用**。
- **修法(定案)**:
  - 任务图:`GET /tasks/{id}/image?kind=original|result`
  - 聊天图:`GET /chat/images/{image_id}`
  - 后端按资源 ID 查所有权后返回 `FileResponse`;非本人 404。
  - 前端以带 Authorization 的请求取 Blob,再 `URL.createObjectURL` 展示;封装成通用 hook/组件。
  - 公开资源(logo 等)单独白名单目录,仍可静态挂载。
- **验收**:未带 token 或非本人访问一律 404/401;页面图片全部正常显示;直连旧 `/static` 上传路径不再可达。

### 2.2 聊天 `task_id` IDOR——校验位置必须提前

- **现状**:外来 `task_id` 在验证所有权**之前**已被:写入用户消息、用于查询历史、用于获取检测上下文(`routers/chat.py:197-216` 只是最后一处)。
- **修法(定案)**:在**获取聊天锁与写入任何消息之前**完成归属校验;非本人统一 404(不用 403,避免泄露任务存在性)。
- **回归测试**:失败请求**不得落下任何脏消息**(用户消息、历史、上下文均无残留)。

### 2.3 CORS 收紧

`allow_origins=["*"]` 且 `allow_credentials=True`(`main.py:75-80`)→ **复用已存在的 `settings.ALLOWED_ORIGINS`(`config.py:31`,当前定义了但未接入 CORS 中间件)**,并在 `.env.example` 补该项示例。

### 2.4 聊天锁重造(审查补充了一个真并发 bug)

- **现状**:锁值固定 `"1"`、TTL 恰好 120s、流结束后无条件 delete。**若第一条流超过 120s,第二条请求取得新锁;第一条结束时会把第二条的锁删掉。**另有:进入 `StreamingResponse` 前抛错不走 `finally`,锁泄漏卡用户约 120s。
- **修法(定案,二审修订——生命周期逐段写死,不留选项)**:
  - 锁值使用唯一 token(每请求随机)
  - 释放一律用 Lua compare-and-delete,只删自己的锁
  - **TTL = `RAG_STREAM_TOTAL_TIMEOUT_S` + 60(即 180s);本轮不做续租**
  - 图片类型/大小等**全部可做的输入校验移到加锁前**
  - **加锁后、流开始前**的准备阶段异常:立即 compare-and-delete 释放
  - **流式阶段**:由 `event_generator` 自己在 `finally` 中释放
  - ⛔ **不得在路由函数外层包 `try/finally`**:`return StreamingResponse(...)` 时外层 `finally` 立即执行,流还没开始锁就没了
- **回归测试**:①「旧请求不得删除新请求的锁」②准备阶段异常不泄漏锁 ③流正常/异常结束均释放。

### 2.5 凭证与口令策略(审查裁定:不做半套)

- **本轮只缩短 access token 有效期**(7 天 → 如 2h,可配),**不引入 refresh/滑动续期**(要做就做完整方案,本轮不做)。
- 注册密码规则(三审更正事实:本项目用 `pwdlib[argon2]` 的 `PasswordHash.recommended()` = **Argon2,不存在 bcrypt 72 字节上限**):**最小长度 8、最大长度 128(防异常超长输入),不做大小写/符号组合规则**;前后端同步校验与提示(`schemas/user.py:16`)。

### 3.1 多会话管理(设计补全,审查要求)

- **为什么**:聊天现状只有「自由问答/按 taskId 一条线」,无会话列表,demo 与回看都难。
- **数据模型(定案)**:
  - `Conversation`:`id`、`user_id`(FK,必填)、`task_id`(FK,可空;**非空即作为会话级上下文**,该会话内聊天自动携带此任务的检测上下文)、`title`、`created_at`
  - `ChatMessage` 增加 `conversation_id`(FK)
  - **既有 `ChatMessage.task_id`(`models/chat.py:19`)的处置(二审定案,防两个真相源)**:迁移后保留为**只读历史兼容字段**并注释标记 deprecated;**新消息不再写入**;所有会话级上下文判断只看 `Conversation.task_id`,它是唯一真相源。
- **旧数据回填(Alembic 迁移,upgrade 与 downgrade 都必须实现)**:按 `(user_id, ChatMessage.task_id)` 分组,每组建一个会话并回填 `conversation_id`;`task_id` 为空的自由问答,每用户归入一个「历史对话」会话。
- **downgrade 不得丢任务关联(三审 P1)**:因新消息不再写 `ChatMessage.task_id`,downgrade **必须先把 `Conversation.task_id` 回填至该会话所有消息的 `ChatMessage.task_id`**,然后才删除 conversation 表与 `conversation_id` 列;消息保留。
- **授权与级联**:所有 conversation 接口校验 `user_id` 归属;删除会话级联删除其消息。
- **前端**:聊天页左侧会话列表(新建/重命名/删除);标题默认取首条消息截断,不做自动摘要。
- **验收**:两个会话互不串历史;级联删除;迁移可 upgrade/downgrade 往返;非本人会话 404。

### 3.2 检测结果结构化导出

- 任务详情加「导出 JSON / CSV」;数据从既有 `detect_result` 序列化,不重跑检测;文件名含任务 id 与时间戳。
- **字段固定(二审要求)**:`task_id`、`image_name`、`defect_class`、`confidence`(保留 4 位小数)、`bbox_x1/y1/x2/y2`、`detected_at`。JSON 顶层为 `{"task_id": ..., "detections": [...]}`;CSV 首行为上述表头。
- **空结构固定**:无检出时 JSON 为 `{"task_id": ..., "detections": []}`,CSV 只有表头行;均正常 200,不报错。
- 验收:导出与页面一致;空结果按上述固定结构返回。

### 3.3 「关联问答」小升级(审查更正:此功能已存在,不得称新闭环)

- **现状**:任务详情已有「关联问答」入口跳 `/chat?taskId=...`,聊天页已使用 task 上下文。
- **三审更正:后端已把 `task.detect_result` 作为 `image_context` 传给 RAG(`chat.py:195-200`),⛔ 不得再持久化一条伪造的「首条摘要消息」——那是重复能力。**
- **增量(仅此两点,均在前端/展示层)**:①聊天页展示「当前任务缺陷摘要」**上下文卡片**(数据来自任务详情,纯展示,不落库);②预置 2-3 个快捷问题(如「X 类缺陷怎么修?」)。后端继续复用现有 `image_context`,并复用 2.2 修好的归属校验。
- **验收(拆成可判定两层)**:
  - **自动测试**:上下文卡片渲染出该任务的缺陷类别与数量(前端测试);带 taskId 的提问 task 已鉴权(非本人 404);响应 `route=rag` 或 `meta.sources` 非空(证明 `image_context` 生效)。
  - **人工 demo**:首答内容是否合理引用检修方案——受模型随机性影响,**不作硬闸**。
