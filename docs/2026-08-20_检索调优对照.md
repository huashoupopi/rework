# 检索调优对照（P2，2026-08-20）

> 规格：[可观测性与检索调优设计 v2](https://github.com/huashoupopi/rework/blob/feat/observability-design/docs/2026-08-20_%E5%8F%AF%E8%A7%82%E6%B5%8B%E6%80%A7%E4%B8%8E%E6%A3%80%E7%B4%A2%E8%B0%83%E4%BC%98%E8%AE%BE%E8%AE%A1.md) §三。
> ⛔ 基线是**并发接管融合之后**重跑的，不是设计文档 §1.3 的旧数字。

## 背景：总时长不能当 A/B 尺子

P1 全量 36 题里，走完五跳的 31 道中有 30 道在跑 rewrite。架构台按 P1 结果核算：rewrite 累计 222 秒，占链路总时长 39%。根因是 eval 共用一个账号，R01 之后会话窗口非空，改写门卫（有历史且 ≤40 字）几乎每题都开火。

本对照四组检索层复现了同一现象：每组 10 题 rewrite 全跑（0 跳过），rewrite 占该组 total_ms 的 34%–37%。retrieve+rerank 只占 8%–9%。

**因此对照只看两件事**：① hit@10 / hit@5 / MRR ② trace 里 retrieve+rerank 两跳耗时。不看 wall clock / total_ms。

## 实验设置

| 项 | 值 |
|---|---|
| 题 | eval30 检索层 R01–R10，10 题 |
| 并发 | `asyncio.gather` 纯向量 `default` + 纯全文 `sparse` |
| 基线融合 | concat：dense 在前、sparse 在后，按 node id 去重（对齐库 `_dedup_results`） |
| RRF | `score(d)=Σ 1/(k+rank_i(d))`，k ∈ {10, 60, 100} |
| 兜底 | 两路都空 → 纯向量 + 未分词 `augmented_question` |
| 超参 | `RETRIEVAL_TOP_K=10` `RERANK_TOP_N=5` `SOURCE_THRESHOLD=-6.0` |
| 账号 | 与 P1 相同共用账号（rewrite 污染故意保留，不改评测协议） |

### k=10 与 k=100 的 MRR 相同不是巧合

架构台复核：10 题里 **8 题逐题 MRR 相同**，只有 R01/R02 互换。不是随机抖动。

根因是两路重叠低（约 15%–35%）。只出现在一路里的文档，RRF 分数只有一项 `1/(k+rank)`；k 同时乘在分母上，**组内相对名次与 k 无关**。k 只作用在那 3–7 条重叠文档上，样本太少，被单路文档稀释掉。

所以 k 扫 10/60/100 几乎看不见差。这条比「抖动」更能回答面试追问。

P3 起 retrieve 跳直接记 `dense` / `sparse` / `overlap`，不必再用 `returned` 反推重叠。
默认 k=10 收口全量 `eval30_20260820_235153_p3-after.json` 的 10 道检索题：overlap 4–7（相对 20 条两路槽位 = 20%–35%），与当时用 `returned` 反推一致。

## 结论

**不启用 RRF，生产默认保持 `RAG_FUSION_MODE=concat`。**

理由：本题库检索层已经 10/10、hit@5=1.0，RRF 没有把命中再抬上去。k 扫不动排序，是因为重叠太少、单路文档的 RRF 分与 k 无关（见上节），不是实现写错。实现留下、用环境变量可切，换重叠更高的题库再测。

「做了就要用」不成立。
