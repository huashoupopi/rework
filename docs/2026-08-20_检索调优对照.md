# 检索调优对照（P2，2026-08-20）

> 规格：[可观测性与检索调优设计 v2](https://github.com/huashoupopi/rework/blob/feat/observability-design/docs/2026-08-20_%E5%8F%AF%E8%A7%82%E6%B5%8B%E6%80%A7%E4%B8%8E%E6%A3%80%E7%B4%A2%E8%B0%83%E4%BC%98%E8%AE%BE%E8%AE%A1.md) §三。
> ⛔ 基线是**并发接管融合之后**重跑的，不是设计文档 §1.3 的旧数字。

## 背景：总时长不能当 A/B 尺子

P1 全量 36 题里，走完五跳的 31 道中有 30 道在跑 rewrite。架构台按 P1 结果核算：rewrite 累计 222 秒，占链路总时长 39%。根因是 eval 共用一个账号，R01 之后会话窗口非空，改写门卫（有历史且 ≤40 字）几乎每题都开火。

本对照四组检索层复现了同一现象：每组 10 题 rewrite 全跑（0 跳过），rewrite 占该组 total_ms 的 34%–37%。retrieve+rerank 只占 8%–9%。

**因此对照只看两件事**：① hit@10 / hit@5 / MRR ② trace 里 retrieve+rerank 两跳耗时。不看 wall clock / total_ms。

## 实验设置

| 项 | 值 |
|---|---|
| 题 | eval30 检索层 R01–R10，10 题 |
| 并发 | `asyncio.gather` 纯向量 `default` + 纯全文 `sparse` |
| 基线融合 | concat：dense 在前、sparse 在后，按 node id 去重（对齐库 `_dedup_results`） |
| RRF | `score(d)=Σ 1/(k+rank_i(d))`，k ∈ {10, 60, 100} |
| 兜底 | 两路都空 → 纯向量 + 未分词 `augmented_question` |
| 超参 | `RETRIEVAL_TOP_K=10` `RERANK_TOP_N=5` `SOURCE_THRESHOLD=-6.0` |
| 账号 | 与 P1 相同共用账号（rewrite 污染故意保留，不改评测协议） |

## 检索质量

| 组 | 文件 | 通过 | hit@10 | hit@5 | MRR |
|---|---|---|---|---|---|
| concat 基线（并发后重跑） | `eval30_20260820_191935_baseline.json` | 10/10 | 1.0 | 1.0 | 0.774 |
| RRF k=60 | `eval30_20260820_192344_rrf-k60.json` | 10/10 | 1.0 | 1.0 | 0.769 |
| RRF k=10 | `eval30_20260820_192741_rrf-k10.json` | 10/10 | 1.0 | 1.0 | 0.835 |
| RRF k=100 | `eval30_20260820_193126_rrf-k100.json` | 10/10 | 1.0 | 1.0 | 0.835 |

搬家后、尚未改融合的全量：`eval30_20260820_191321_param-move.json` **36/36**，检索 10/10、MRR 0.757。

P2 默认 concat 收口全量：`eval30_20260820_194549_p2-after.json` **36/36**，检索 10/10、MRR 0.761。

P1 全量检索 MRR 是 0.824。同一套 10 题、hit@5 已经封顶，MRR 在 0.757–0.835 之间晃，幅度和「换融合」同量级，解释不了是 RRF 的功劳。

## 耗时（trace 单跳，单位 ms，10 题均值）

| 组 | retrieve | rerank | retrieve+rerank | rewrite（对照，不参与结论） |
|---|---|---|---|---|
| concat 基线 | 160.0 | 1586.5 | **1746.5** | 7572.3 |
| RRF k=60 | 200.9 | 1556.2 | **1757.1** | 7330.4 |
| RRF k=10 | 166.5 | 1553.7 | **1720.3** | 7640.3 |
| RRF k=100 | 162.8 | 1545.7 | **1708.4** | 6509.9 |

融合本身在 1.7s 的 retrieve+rerank 里看不出稳定差距。总时长被 rewrite 淹掉，不采用。

## 结论

**不启用 RRF，生产默认保持 `RAG_FUSION_MODE=concat`。**

理由：本题库检索层已经 10/10、hit@5=1.0，RRF 没有把命中再抬上去；MRR 波动落在既有 run-to-run 噪声里。实现留下、用环境变量可切，方便以后换题库再测。

「做了就要用」不成立。

## 归因段

检索四组 + 收口全量都是 36/36 或 10/10，没有红题。P1 欠着的「失败归因」手动验收这次仍没机会顺手验（报告在全绿时不打印该段）。单元测试 `test_print_report_failure_traces` 仍覆盖该段。
