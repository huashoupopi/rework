## 1. 背景与目标

本项目后端已经形成明确的三条业务线：

1. 缺陷检测任务
2. 流式聊天问答
3. 管理员知识库运维

新前端已经在 `frontend/myapp` 下以 Vite 初始化，但当前仍是最小骨架。用户希望前端整体方向参考 `bs` 项目，但不是照搬旧实现，而是基于当前后端接口与架构做一次优化与重写。

本规范只解决前端基础层问题：

- 目录结构
- 路由地图
- 权限框架
- 状态管理边界
- 请求层边界
- UI 栈边界
- 依赖清单

本规范不展开业务页细节，不覆盖任务中心、聊天模块、知识库页面的逐交互设计。这些内容会进入后续子规范。

## 2. 已确认约束

### 2.1 产品与交互约束

- 前端继续采用单一 `SPA` 设计，不拆用户端 / 管理端双入口。
- V1 严格贴当前后端能力，不为了保留 `bs` 的首页形态额外设计重统计看板。
- `Detect` 与 `History` 不再拆为两页，合并为统一的“任务中心”。
- 前端定位为混合型产品：
  - 主体是后台型业务界面
  - 登录、首页、聊天等关键页面需要更产品化的体验
- 视觉方向参考 `Apple` 的“液态玻璃”设计语言，但只作为灵感源，不做全站重玻璃化复制。

### 2.2 参考项目约束

用户明确指定 `bs` 作为参考，其优先级为：

1. 页面与路由结构优先
2. 技术组织优先
3. 视觉与交互风格优先

这意味着 `bs` 只能作为信息架构与组织方式的参考，不能作为接口真相来源。当前后端与 `bs` 的部分接口已存在明显偏差，尤其体现在认证、知识库与任务相关接口上。

### 2.3 技术约束

- 包管理器：`pnpm`
- 开发语言：`JavaScript`
- UI 相关：`shadcn/ui + Tailwind CSS v4 + Antd`
- 请求库：`axios`
- 当前脚手架：`Vite + React`

## 3. 方案比较

### 方案 A：高度复刻 `bs`

特征：

- 页面拆分尽量保持原状
- 目录与 store 结构延续旧项目
- 旧接口适配逻辑尽量兼容

优点：

- 上手快
- 对已有参考的心理负担最小

缺点：

- 会直接继承旧项目的接口假设与状态耦合
- 任务、聊天、知识库三类异步模型容易继续堆进大 store
- 与当前后端边界不匹配

### 方案 B：完全产品化重做

特征：

- 弱化后台味道
- 强化品牌感、视觉一致性和定制组件
- `shadcn/ui + Tailwind` 作为绝对主导

优点：

- 视觉上最干净
- 后续品牌扩展空间大

缺点：

- 与当前业务密度不匹配
- 管理类页面会失去 Antd 的效率优势
- V1 成本高，偏离当前目标

### 方案 C：单 SPA + 业务域分层 + 混合 UI 栈

特征：

- 单一 SPA
- 页面结构参考 `bs`
- 任务中心合并
- 轻全局状态
- `shadcn/ui + Tailwind` 负责外壳与关键体验页
- `Antd` 负责高密度业务组件

优点：

- 最贴近当前后端与目标
- 比方案 A 更易维护
- 比方案 B 更务实

缺点：

- 视觉语言不是绝对统一的一套体系
- 需要明确 UI 栈边界，否则容易混乱

## 4. 最终决策

采用方案 C：

> 单 SPA + 业务域分层 + 轻全局状态 + 混合 UI 栈

这是当前最优路径，原因如下：

1. 它保留了 `bs` 中最有价值的部分：信息架构和开发组织习惯。
2. 它避免继承 `bs` 的主要问题：大状态、页面职责割裂、旧接口假设。
3. 它与当前后端真实边界一致，不会为了前端结构美观去扭曲后端能力。
4. 它能在 V1 内控制成本，同时为后续任务中心、聊天、知识库子规范留出清晰扩展位。

## 5. 前端总体架构

前端采用单页应用，按照“应用壳 + 业务域模块”的方式组织。

### 5.1 总体结构

```text
frontend/myapp/src
├── app/                    # 应用装配层
├── layouts/                # 框架布局
├── pages/                  # 页面入口层
├── features/               # 按业务域组织
├── shared/                 # 共享组件、hooks、utils、常量
└── lib/                    # 通用底层能力（如 cn、http 适配器）
```

### 5.2 分层职责

- `app/`
  - 应用入口装配
  - provider 注入
  - 路由注册
  - 全局异常边界与初始化逻辑

- `layouts/`
  - 主框架布局
  - 导航栏、侧边栏、页面容器
  - 权限化菜单显示

- `pages/`
  - 只作为路由级页面入口
  - 不承载大量跨页面复用逻辑
  - 负责拼装对应 feature 模块

- `features/`
  - 业务域实现中心
  - API、hooks、状态、组件优先在域内闭环

- `shared/`
  - 真正跨业务域复用的能力
  - 例如通用空状态、下载工具、时间格式化、权限判断

- `lib/`
  - 通用底层工具
  - 不含具体业务语义

## 6. 路由设计

### 6.1 路由原则

- 保持单 SPA
- 继承 `bs` 的信息架构主线，但按当前后端边界重排
- 用户态与管理员态共用同一套路由系统
- 权限通过“菜单控制 + 路由拦截”双层处理

### 6.2 V1 路由地图

```text
/login
/register
/
/tasks
/tasks/:taskId
/chat
/knowledge/documents
/knowledge/rebuild
/knowledge/chunk-configs
/users
```

### 6.3 页面职责

- `/login`
  - 登录页
  - 产品化呈现优先

- `/register`
  - 注册页
  - 与登录页风格统一

- `/`
  - 轻量工作台首页
  - 提供最近任务、快捷入口、当前状态提醒
  - 不承担重统计 Dashboard 职责

- `/tasks`
  - 任务中心
  - 负责上传、列表、筛选、轮询、批量操作入口

- `/tasks/:taskId`
  - 任务详情
  - 展示结果图、缺陷结果、单任务下载入口、进入关联聊天

- `/chat`
  - 聊天页
  - 支持普通聊天
  - 支持通过 `search params` 方式接收 `taskId` 上下文

- `/knowledge/documents`
  - 管理员文档管理页

- `/knowledge/rebuild`
  - 管理员索引重建与状态页

- `/knowledge/chunk-configs`
  - 管理员分块配置页

- `/users`
  - 管理员用户管理页

### 6.4 权限策略

- 所有业务页必须经过登录校验
- 管理员页通过 `is_superuser` 控制访问
- 权限控制包含两层：
  - 菜单隐藏
  - 路由级访问拦截

仅做菜单隐藏而不做路由拦截是不允许的。

## 7. 模块边界

基础层之后的业务模块按域拆分，至少包含以下模块：

```text
features/
├── auth/
├── shell/
├── task-center/
├── chat/
├── knowledge-admin/
└── user-admin/
```

### 7.1 模块职责

- `auth`
  - 登录、注册、鉴权守卫
  - 当前用户信息

- `shell`
  - 主布局、导航、面包屑、权限菜单

- `task-center`
  - 上传
  - 列表
  - 轮询
  - 详情适配

- `chat`
  - 流式聊天
  - 历史消息
  - `taskId` 上下文接入

- `knowledge-admin`
  - 文档管理
  - 重建状态
  - chunk config

- `user-admin`
  - 用户列表与管理员操作

### 7.2 跨模块通信原则

跨模块优先使用以下方式：

1. `route params`
2. `search params`
3. 显式 API 调用
4. 共享底层工具

不允许让 `task-center` 直接持有 `chat` 页面状态，也不允许为了方便跳转而把业务主状态提升到全局 store。

## 8. 状态管理策略

### 8.1 总体策略

状态管理采用 `zustand`，但只用于最小全局状态。

### 8.2 全局状态允许范围

允许进入全局 store 的内容：

- `token`
- `userInfo`
- `auth hydrated`
- 应用壳少量 UI 状态
  - 例如侧边栏折叠
  - 最近访问菜单

### 8.3 禁止进入全局 store 的内容

以下状态默认禁止放入全局 store：

- 任务列表
- 任务轮询状态
- 当前页筛选结果
- 聊天消息
- 流式输出中间态
- 知识库文档列表
- 重建轮询结果

这些状态应优先保留在：

- 页面内状态
- feature 内 hooks
- 路由参数

### 8.4 持久化原则

- 仅持久化认证最小集
- 不持久化业务主状态
- 不为了“刷新保留上下文”把复杂业务数据直接写入 `localStorage`

## 9. 请求层设计

### 9.1 总体策略

标准请求统一走 `axios`。

建议结构：

```text
src/shared/api/http.js          # 共享 axios 实例
src/features/*/api/*.js         # 业务域 API 封装
```

### 9.2 共享 HTTP 客户端职责

共享 HTTP 客户端只负责：

- `baseURL=/api`
- Bearer Token 注入
- 401 统一处理
- 通用错误提示映射
- 文件下载支持

共享客户端不承担业务解包逻辑，不承担页面级数据拼装。

### 9.3 业务 API 组织方式

API 应按业务域组织，而不是继续堆在一个顶层杂糅目录中。

建议形态：

```text
features/auth/api/
features/task-center/api/
features/chat/api/
features/knowledge-admin/api/
features/user-admin/api/
```

### 9.4 聊天流式接口的例外

`/chat/stream` 不应强行走 `axios`。

原因：

- 当前后端返回的是 `text/plain` 流
- 不是普通 JSON 接口
- 也不是标准 SSE
- 浏览器端增量消费更适合 `fetch + ReadableStream`

因此请求层结论如下：

- `axios` 是主请求库
- `fetch` 只作为聊天流接口的特例

## 10. UI 栈边界

### 10.1 采用混合 UI 栈

本项目采用：

- `shadcn/ui + Tailwind CSS v4`
- `Antd`

但两者必须分工明确。

### 10.1.1 视觉基调

视觉风格参考 `Apple` 的“液态玻璃”语言，但采用克制版落地，而不是全站铺满模糊、半透明和高反射特效。

设计目标：

- 整体观感更优雅、轻盈、现代
- 保留后台产品所需的清晰信息层级
- 不牺牲表格、表单、状态标签和业务操作的可读性

落地原则：

- 将液态玻璃感优先用于：
  - 登录页
  - 注册页
  - 首页卡片
  - 顶部导航和侧边导航容器
  - 聊天区域的消息容器、输入区或悬浮层
- 不将液态玻璃作为高密度业务页面的默认背景方案
- 在任务中心、知识库、用户管理等页面中，业务表格和表单区域仍以实色背景、明确边框和稳定对比度为主
- 允许使用：
  - 轻度透明
  - 柔和模糊
  - 分层高光
  - 柔阴影和大圆角
- 不鼓励使用：
  - 大面积强模糊
  - 低对比文字覆盖在复杂背景上
  - 为了“像 Apple”牺牲信息密度和扫描效率

### 10.2 shadcn/ui + Tailwind 负责

- 登录页
- 注册页
- 主框架壳
- 导航
- 卡片
- 空状态
- 聊天容器
- 产品化感更强的轻交互区域

### 10.3 Antd 负责

- Table
- Upload
- Form
- Pagination
- Drawer
- Modal
- Popconfirm
- Message
- Tag
- Spin

### 10.4 使用原则

- 一个复杂业务块只允许一套主组件体系
- 不在同一张核心表单里混用两套输入控件
- Antd 负责业务密度
- shadcn/ui 负责结构外壳与关键体验

### 10.5 样式策略

- 默认以 `Tailwind v4` 为主
- 使用 CSS 变量统一基础语义色、圆角和主题语义
- 通过 `Antd ConfigProvider` 做最小主题对齐
- 不延续 `bs` 中“页面级 SCSS 到处开”的做法
- 将“液态玻璃”效果收敛为少量可复用视觉 token 或样式语义，而不是页面各自随意实现

### 10.5.1 视觉实现约束

为了避免后续页面风格漂移，视觉实现需遵循以下约束：

- 玻璃态效果必须组件化或 token 化
- 同一页面中玻璃态层级不超过 1 到 2 个主层
- 文字与背景的对比度必须优先于视觉效果
- 业务核心区域的首要目标是“可读、可扫、可点”，不是“像演示稿”
- 任务中心、知识库、用户管理页的表格主体默认不使用玻璃底

### 10.6 局部样式例外

只有以下场景允许保留局部 CSS 文件：

- 第三方组件样式覆盖困难
- 画布类组件
- 复杂可视化组件

`Sass/SCSS` 不作为 V1 默认依赖。

## 14. 风险与预警

### 风险 1：把 `bs` 当模板而不是参考

信号：

- 前端开始出现大量“兼容旧接口”的判断
- 新项目 API 命名仍按旧后端写

应对：

- 以当前 `rework` 后端为唯一接口真相

### 风险 2：全局状态失控

信号：

- 任务轮询、聊天流、知识库状态开始进全局 store

应对：

- 保持“认证全局、业务局部”原则

### 风险 3：UI 栈边界失守

信号：

- 同一业务区块同时混用 Antd 表单与自定义 Tailwind 表单

应对：

- 坚持“一个复杂业务块一套主组件体系”的规则
