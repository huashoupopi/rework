## 〇、立项依据与一条必须先讲的事实更正

### 0.1 为什么是可观测性

[2026-08-14 JD 与面经情报](../../arch/2026-08-14_JD与面经情报.md) 的结论（原文）：

- Kimi JD 把 `Observability` 列进**基本机制**，加分项再列一次 `Trace Analysis`
- 11 项基本机制覆盖 9.5/11，**唯一系统性空白就是 Observability**
- 情报原话：**「可观测性不只是加分，它是失败归因的前提」**

**该缺口在本项目有实证**：2026-08-19 修 eval 检索层三道红题（R06/R09/R10）时，定位靠的是人肉读日志加推测，最后才发现根因是「NFKC 管不到 ⻮」与「FTS 没做中文分词」。**有结构化链路数据的话，这两跳会直接暴露在数据里。**

### 0.2 ⚠️ 一条必须先纠正的事实（本设计的直接起因之一）

**读 llama-index 源码实测**（`llama_index/vector_stores/postgres/base.py:1030` `_hybrid_query`）：

```python
if query.alpha is not None:
    _logger.warning("postgres hybrid search does not support alpha parameter.")
dense_results  = self._query_with_score(...)       # 向量
sparse_results = self._sparse_query_with_rank(...) # 全文
all_results = dense_results + sparse_results       # 直接拼接
return _dedup_results(all_results)                 # 只按 node_id 去重（:1356，全文 7 行）
```

**结论：本项目的混合检索链路里没有 RRF，也没有任何融合排序。** 向量结果在前、全文结果在后，去重时保留先出现的那条。`alpha` 参数被库明确声明不支持。

**已产生的后果**：简历与考纲表此前都写了「RRF 融合」「RRF 权重可复述」——**那个参数不存在，问起来答不出**。简历措辞已于 2026-08-20 更正（详见 §五）。

**这条同时是 P2 的立项理由**：要能讲「融合怎么做的」，就得真的有一个融合实现。

## 二、P1：RAG 链路结构化 trace + eval 失败归因

### 2.1 目标

一次问答产出**一条结构化 trace**，覆盖全部关键跳；eval 跑完后，每道红题能直接看出**是哪一跳出的问题**，不必读日志推测。

### 2.2 设计

**开关**：复用既有 `RAG_EVAL_DEBUG`，⛔ **不新增第二个开关**——两个开关会立刻产生「开了一个没开另一个」的组合态。
生产默认关闭；关闭时**除一次 `if` 判断外零开销**，⛔ 不许在关闭时仍构造 trace 对象再丢弃。

**结构**（`meta["rag_trace"]`）：

```jsonc
{
  "request_id": "…",              // 复用 get_request_id()，与日志行可对照
  "total_ms": 8123.4,
  "steps": [
    { "step": "rewrite",  "ms": 412.0, "skipped": true,
      "reason": "no_history",     // 或 "heuristic_skip"
      "original": "…", "rewritten": "…" },
    { "step": "retrieve", "ms": 980.5, "mode": "hybrid",  // 或 "fallback_dense"
      "query": "…", "tokenized_query": "…",               // jieba 分词后的实际 FTS 查询
      "returned": 10, "top_score": -1.23 },
    { "step": "rerank",   "ms": 1500.2, "in": 10, "out": 5,
      "moved": [ { "from": 3, "to": 1 }, … ] },            // 名次变化，用于判断重排是否把正确文档挤下去
    { "step": "route",    "ms": 2.0, "route": "rag",
      "context_nodes": 4, "top_score": -1.23, "injection_score": 0 },
    { "step": "generate", "ms": 5200.0, "ttfb_ms": 1200.0, "mode": "chat",
      "finish_reason": "stop" }
  ]
}
```

**取舍与理由**：

| 决策 | 理由 |
|---|---|
| trace 走 `meta` 而非独立接口 | eval 已从 `meta` 取数（`send_chat:146`），这条路已验证；新开接口要重做鉴权与取数 |
| `retrieval_debug` **保留不动** | eval 检索层判分正依赖它（`scoring.py:132` `score_retrieval` 在 chunk 全文里找 term）。⛔ **改它会打断 36/36 的判分**。`rag_trace` 是**并列新增**，不是替换 |
| trace 里 **不放 chunk 全文** | `build_debug_nodes` 的注释已说明全文会显著放大消息体积；全文由 `retrieval_debug` 承担，trace 只放名次与分数 |
| `moved` 只记名次变化 | 判断「重排把正确文档挤下去」只需要名次，不需要内容 |
| ⛔ 不引入 OTel / Jaeger | 见 §0.3 |

### 2.3 eval 侧消费

1. `run_rag_eval.py` 把 `meta["rag_trace"]` 原样写进单条结果（新增字段 `trace`）
2. 报告新增**红题归因摘要**：对每道非 PASS 用例，打印它的 `steps` 摘要（各跳 ms / 关键字段），⛔ **不做自动"诊断结论"**——那会变成猜测；只把事实摆出来，判断归人
3. `print_report` 增加一段「失败归因」，红题为空时该段不出现

### 2.4 验收（缺一不可）

- [ ] `RAG_EVAL_DEBUG=0`（默认）时 `meta` 里**没有** `rag_trace` 键；且代码路径上不构造 trace 对象
- [ ] `RAG_EVAL_DEBUG=1` 时，一次问答的 trace 覆盖 5 跳，`sum(steps.ms)` 与 `total_ms` 的差 < 100ms（差值来自未计跳，需能解释）
- [ ] `request_id` 与同一次请求的日志行一致（实测比对，不是断言字段存在）
- [ ] **全量 eval 仍是 36/36** ← 硬闸，trace 不得改变任何判分行为
- [ ] 故意制造一道红题（如临时把 `RETRIEVAL_TOP_K` 调到 1），报告的归因段能显示出是哪一跳异常
- [ ] 新增测试：trace 结构、开关关闭时不产出、`retrieval_debug` 未被破坏

## 三、P2：实现 RRF 融合 + 超参可配 + eval A/B 对照

### 3.1 目标

把 §0.2 那个「没有融合排序」的事实，变成**一次有数据的改造**：自己实现 RRF，用 eval 量前后差异。

### 3.2 设计

**第一步：把融合从库里接管出来**

现状是 `as_retriever(vector_store_query_mode="hybrid")` 一把梭。改为：

1. 分别取向量结果与全文结果（各自 `top_k`）
2. 自己做 RRF 融合：`score(d) = Σ 1/(k + rank_i(d))`，`k` 可配（业界常用 60）
3. 融合后再进 rerank

⚠️ **执行前必须先确认**：llama-index 的 `PGVectorStore` 是否暴露了「只做向量」与「只做全文」的独立入口。
- `vector_store_query_mode="default"` = 纯向量（代码已在用，见降级分支 `rag_service.py:450`）
- 纯全文入口**需要执行方自行核实**（`_sparse_query_with_rank` 是私有方法，⛔ **不得直接调用私有方法**）
- **若没有公开入口**：停下上报，不要自己 monkey-patch 或复制库代码。届时退回方案 B（见 §3.5）

**第二步：超参集中可配**

`RETRIEVAL_TOP_K` / `RERANK_TOP_N` / `SOURCE_THRESHOLD` 从类属性移入 `settings`，与 `CHUNK_SIZE` 等并列；新增 `RRF_K`。
⛔ **默认值必须与当前值完全一致**（10 / 5 / -6.0），本步是纯搬家，不得顺手调参。

**第三步：A/B 对照**

`run_rag_eval.py` 增加 `--tag <name>`，把标签写进结果文件名与报告，便于对照。
⛔ **不做「自动跑多组参数」的批量框架**——那是脚手架工程，收益低。手动改环境变量跑两次即可。

### 3.3 必须留下的数据

至少三组对照，每组跑**检索层 10 题**（3.3 分钟/组）：

| 组 | 变量 |
|---|---|
| 基线 | 当前行为（拼接去重） |
| RRF k=60 | 融合改 RRF |
| RRF k=10 / k=100 | 看 k 的敏感度 |

**结果写进 `docs/2026-08-20_检索调优对照.md`**，含每组的 `hit@5` / `hit@10` / `MRR`。
⚠️ **如果 RRF 没有带来改善，如实记录并保留基线行为**。⛔ 不许因为「做了就要用」而强行切换——「我实现了 RRF，实测在本题库上与拼接去重无显著差异，所以没上」同样是好答案，且更可信。

### 3.4 验收

- [ ] 三组对照数据齐备，写入对照文档
- [ ] 融合逻辑有单元测试（给定两路 rank，验证 RRF 输出顺序），⛔ 不依赖真实检索
- [ ] 超参搬家后默认行为与搬家前**完全一致**（全量 eval 仍 36/36）
- [ ] 最终是否启用 RRF 由数据决定，并在文档写明理由

### 3.5 方案 B（若无公开的纯全文入口）

保持 `hybrid` 调用不变，但在**拿到结果之后**用自己的逻辑重排：
利用 `retrieval_debug` 已有的名次信息，按「向量段」与「全文段」的边界还原两路 rank，再做 RRF。
⚠️ 此方案依赖对库返回顺序的假设（dense 在前、sparse 在后），**必须先用实测验证该假设成立**，验证不了就停下上报。

## 四、P3：评测与链路可视化页面

### 4.1 目标

前两条的产出都只存在于 JSON 文件里。**面试官不会翻 `evals/results/*.json`。** 做一页让它可见。

### 4.2 设计

**路由**：`/evals`，放在管理区（与知识库三页同级），仅 superuser 可见。

**数据来源（二选一，执行方先说选哪个及理由）**：
- ⑴ 新增只读接口，后端扫 `evals/results/*.json` 返回列表与详情
- ⑵ 构建期把结果拷进前端静态资源

**倾向 ⑴**，理由：⑵ 会让页面数据与仓库状态脱节，且每次跑完 eval 都要重新构建。
⚠️ ⑴ 必须做**路径穿越防护**：只允许读 `evals/results/` 下的 `.json`，文件名白名单化（⛔ 不得把用户输入直接拼进路径）。

**页面内容**：
1. 历次跑批列表（时间、总分、分层得分）
2. 单次详情：五层通过率 + 36 题表格
3. 点开单题：判分明细（`scores`）+ **链路 trace（P1 的产出）**
4. 红题高亮
