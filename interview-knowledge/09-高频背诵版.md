## 一、项目总述：先把整条故事讲顺

### Q1：一句话介绍你的项目

**一句话结论：**
这是一个以 FastAPI 为后端、PostgreSQL 为事务真相源、Redis 为基础设施、Arq 为异步任务系统、PGVector 为检索底座的风电运维智能平台，核心能力包括 RAG 问答、知识库管理和图像目标检测。

**展开 3 点：**
1. 聊天问题走 RAG 链路：检索、重排、生成、流式输出
2. 图片检测和知识库重建走异步任务链路：API 入队，worker 执行
3. PostgreSQL 存业务真相，Redis 承担缓存、锁、限流、黑名单和队列底座

**常见追问：**
- 为什么不是同步处理？
- 为什么选 PostgreSQL + Redis，而不是全塞到一个库里？
- 这个系统最难的部分是什么？

### Q2：这个项目的架构主轴是什么？

**一句话结论：**
主轴不是前端页面，而是 **RAG、后端服务治理、数据库、Redis、异步任务系统** 这 5 条链路。

**展开 3 点：**
1. RAG 负责知识问答与 AI 能力
2. 后端负责 API、流式输出、服务治理和部署边界
3. 数据库 + Redis + 队列共同负责状态、性能和可靠性

**常见追问：**
- 哪一块最有面试价值？
- 哪一块最容易出故障？

## 二、RAG 高频题

### Q3：请你讲一下 RAG 的完整链路

**一句话结论：**
RAG 分成两条链路：离线链路负责构建知识，在线链路负责检索并生成答案。

**展开 3 点：**
1. **离线链路**：文档解析 → chunk 切分 → embedding → 写入 PGVector / 元数据入库
2. **在线链路**：query 预处理 → 混合检索 → rerank → 路由决策 → prompt 组装 → LLM 生成
3. **工程治理**：版本、去重、增量重建、来源引用、权限边界、评测指标

**常见追问：**
- 为什么要把离线和在线分开？
- 为什么不是只做向量检索？
- 为什么检索后还要 rerank？

### Q4：为什么 RAG 不是“调个模型接口”这么简单？

**一句话结论：**
因为真正难的不是调用 LLM，而是 **知识治理、检索质量、延迟成本和错误边界**。

**展开 3 点：**
1. 没有知识治理，索引会脏、旧版本会污染结果
2. 没有 rerank / route / guardrail，回答会跑偏或幻觉
3. 没有评测，你根本不知道优化是不是有效

**常见追问：**
- 怎么评估 RAG 质量？
- RAG 的主要瓶颈是哪里？

### Q5：为什么要混合检索，而不是只用向量检索？

**一句话结论：**
因为语义匹配和精确关键词匹配各有盲区，混合检索是在工程上更稳的折中。

**展开 3 点：**
1. 向量检索擅长语义理解，但对故障码、编号、专有名词可能不够准
2. 关键词检索擅长精确命中，但不擅长近义表达和语义泛化
3. 混合检索再配合 rerank，通常比单路检索鲁棒

**常见追问：**
- RRF 是什么？
- top_k 和 top_n 怎么调？

### Q6：RAG 怎么评估？

**一句话结论：**
至少从检索层、生成层、端到端层三层评估，而不是靠“感觉不错”。

**展开 3 点：**
1. 检索层：Recall@K、MRR、nDCG
2. 生成层：忠实度、答案相关性、引用准确率
3. 端到端：首 token 延迟、总耗时、用户反馈、fallback 占比

**常见追问：**
- 如何构造评测集？
- 离线指标和线上体验不一致怎么办？

### Q7：RAG 和 Fine-tuning 怎么选？

**一句话结论：**
默认先做 RAG，只有当瓶颈真的在模型行为而不是知识获取时，再考虑微调。

**展开 3 点：**
1. RAG 适合知识频繁更新、需要引用来源、隐私敏感场景
2. 微调适合改变模型风格、格式、行为模式
3. 工程上常见顺序是：prompt / RAG / 评测 → 证明不够 → 再考虑微调

**常见追问：**
- 为什么不用 Elasticsearch 直接做问答？
- 什么时候向量库不值得上？

## 三、后端架构与 FastAPI 高频题

### Q8：FastAPI 和 Flask 的本质区别是什么？

**一句话结论：**
核心区别不是语法糖，而是 **ASGI 异步模型 + 类型驱动验证**。

**展开 3 点：**
1. FastAPI 基于 ASGI，适合高并发 I/O
2. Flask 基于 WSGI，更偏同步请求模型
3. FastAPI 的类型系统直接参与参数校验、序列化和文档生成

**常见追问：**
- ASGI 为什么更适合现代 API 服务？
- async 一定更快吗？

### Q9：ASGI 为什么适合你的项目？

**一句话结论：**
因为这个项目大量操作都是 I/O 密集型：数据库、Redis、外部 LLM、文件处理、流式输出。

**展开 3 点：**
1. `await` 可以在等待 I/O 时释放事件循环，提高并发能力
2. HTTP 流式输出这类长连接场景更适合 ASGI；当前项目不是标准 SSE，而是 `text/plain` 流
3. CPU 密集任务不应放在 API 进程，而应放到 worker

**常见追问：**
- 为什么 YOLO 不放 FastAPI 里直接跑？
- `asyncio.to_thread()` 的边界是什么？

### Q10：幂等、超时、重试、熔断、降级分别解决什么问题？

**一句话结论：**
它们是一整套服务治理链路，不是零散概念。

**展开 3 点：**
1. 幂等解决“重复请求造成重复副作用”
2. 超时和重试解决“临时失败怎么收敛”
3. 熔断和降级解决“下游出问题时不要把自己拖死”

**常见追问：**
- 为什么重试必须配幂等？
- 降级和熔断有什么区别？

### Q11：流式响应为什么容易被代理层搞坏？

**一句话结论：**
因为后端能流式产出，不代表中间代理不会把内容缓存住再一次性吐给前端。

**展开 3 点：**
1. 应用层要逐段 yield
2. Nginx / 网关层要关闭 buffering
3. 客户端要按 chunk 增量消费，并处理断连

**常见追问：**
- 为什么要 `X-Accel-Buffering: no`？
- 流式接口怎么做断线处理？

### Q12：可观测性为什么不是“打印日志”就够了？

**一句话结论：**
因为日志、指标、链路追踪回答的是三种不同问题，缺一个都难排障。

**展开 3 点：**
1. 日志：发生了什么
2. 指标：系统现在健康吗
3. Trace：一次请求慢在哪

**常见追问：**
- request_id 和 trace_id 有什么区别？
- SLI / SLO / SLA 怎么区分？

## 四、数据库 高频题

### Q13：为什么选 PostgreSQL，而不是 MySQL？

**一句话结论：**
因为项目既需要关系型事务能力，又需要 PGVector / JSONB 这类扩展能力，PostgreSQL 更合适。

**展开 3 点：**
1. PostgreSQL 事务能力强，适合业务真相源
2. JSONB、扩展生态、SQL 标准能力更强
3. PGVector 让语义检索与业务数据能放在同一套体系里

**常见追问：**
- 那为什么不直接上 Milvus？
- PostgreSQL 做向量检索的边界在哪里？

### Q14：什么是 WAL？为什么 commit 成功不等于数据页已落盘？

**一句话结论：**
因为 PostgreSQL 采用的是“先写 WAL，再异步刷数据页”的持久化策略。

**展开 3 点：**
1. 事务修改数据页时同时生成 WAL
2. commit 时只要 WAL 满足持久化要求，就可以返回成功
3. 崩溃恢复时通过重放 WAL 恢复未刷盘的数据页

**常见追问：**
- Checkpoint 是什么？
- WAL 和备份是一回事吗？

### Q15：什么是 MVCC？

**一句话结论：**
MVCC 通过维护多版本数据和事务快照，实现“读不阻塞写，写尽量不阻塞读”。

**展开 3 点：**
1. 更新不是直接覆盖旧值，而是生成新版本
2. 不同事务根据快照看到不同版本
3. 旧版本要靠 VACUUM / autovacuum 回收，否则会膨胀

**常见追问：**
- 为什么还会有锁？
- 长事务为什么危险？

### Q16：死锁怎么产生？怎么避免？

**一句话结论：**
死锁本质是多个事务获取资源顺序不一致，形成环形等待。

**展开 3 点：**
1. A 先锁 task 再锁 user，B 先锁 user 再锁 task，就可能死锁
2. PostgreSQL 会检测死锁并主动回滚其中一个事务
3. 避免方式是统一加锁顺序、缩短事务、减少热点锁争用

**常见追问：**
- 乐观锁和悲观锁怎么选？
- `SELECT ... FOR UPDATE` 什么时候该用？

### Q17：慢查询怎么查？

**一句话结论：**
靠 `EXPLAIN ANALYZE` 看执行计划，而不是靠猜。

**展开 3 点：**
1. 看是 Seq Scan 还是 Index Scan
2. 看 rows 估算和 actual rows 是否偏差大
3. 看 join 方式、索引命中、返回行数和统计信息是否异常

**常见追问：**
- 为什么建了索引也可能不用？
- 覆盖索引、复合索引怎么设计？

## 五、Redis 高频题

### Q18：Redis 为什么快？

**一句话结论：**
因为它是内存系统，配合 I/O 多路复用、单线程命令执行模型和高效数据结构。

**展开 3 点：**
1. 数据在内存，访问延迟极低
2. epoll/kqueue 让单线程能处理大量并发连接
3. 单线程执行避免锁竞争，CPU 主要花在真正的命令处理上

**常见追问：**
- Redis 6 的多线程改了什么？
- 单线程为什么还能扛高并发？

### Q19：Redis 在你的项目里除了缓存还做了什么？

**一句话结论：**
Redis 在项目里是一库多用：缓存、锁、限流、黑名单、任务结果缓存、Arq 队列底座都用了它。

**展开 3 点：**
1. 它不只是加速层，还是基础设施层
2. 所以故障影响面比普通缓存更大
3. 也正因此更要讲清角色边界和降级策略

**常见追问：**
- Redis 挂了系统怎么办？
- 为什么不拆成多套 Redis？

### Q20：缓存一致性怎么做？

**一句话结论：**
大多数业务系统用 Cache Aside，关键难点不是模式名，而是一致性窗口和热点治理。

**展开 3 点：**
1. 读：先查缓存，miss 再回源数据库
2. 写：先写数据库，再删缓存
3. 高并发下要考虑延迟双删、逻辑过期、多级缓存等工程折中

**常见追问：**
- 缓存穿透/击穿/雪崩怎么处理？
- 为什么更新缓存不如删缓存稳？

### Q21：Sentinel 和 Cluster 的区别？

**一句话结论：**
Sentinel 解决高可用，Cluster 同时解决高可用和水平扩展。

**展开 3 点：**
1. Sentinel 不分片，仍然是单主多从
2. Cluster 把 key 映射到 16384 个 slot 上，分散到多个 master
3. 数据量不大先别上 Cluster，复杂度不值得

**常见追问：**
- 主从复制是同步还是异步？
- 什么情况下该从单机迁到 Cluster？

### Q22：为什么 Lua 脚本比事务更适合释放分布式锁？

**一句话结论：**
因为锁释放需要“读-判断-删”合成一个原子操作，而事务并不擅长这种条件逻辑。

**展开 3 点：**
1. 先 GET 再 DEL 中间可能锁已过期并被别人拿走
2. Lua 可以在 Redis 服务端原子执行条件判断
3. 这是安全释放锁的标准工程做法

**常见追问：**
- Redis 事务为什么不等于数据库事务？
- 分布式锁为什么不能只靠 `DEL`？

## 六、异步任务系统 高频题

### Q23：为什么重任务不能放在 API 里同步做？

**一句话结论：**
因为这样会拖垮请求链路，影响响应时间、并发能力和失败隔离。

**展开 3 点：**
1. YOLO 推理和知识库重建耗时长，容易超时
2. 重任务占 CPU/GPU/线程池，会影响正常 HTTP 请求
3. 异步任务把接入层和执行层分离，系统更稳

**常见追问：**
- 为什么不是 BackgroundTasks？
- API 进程和 worker 进程怎么通信？

### Q24：什么是 at-least-once？

**一句话结论：**
意思是任务至少会被执行一次，但在某些故障窗口下可能被执行多次。

**展开 3 点：**
1. Worker 做完业务动作但来不及 ack，就可能重投
2. 所以可靠队列通常默认不是 exactly-once
3. 工程上要靠幂等设计消化重复执行的副作用

**常见追问：**
- exactly-once 为什么难？
- 幂等键怎么设计？

### Q25：任务失败为什么不能一律重试？

**一句话结论：**
因为临时失败和确定性失败完全不是一回事，无脑重试只会把系统打爆。

**展开 3 点：**
1. 网络抖动、短时超时适合重试
2. 参数错误、权限错误、坏数据不适合重试
3. 要配指数退避、最大重试次数、DLQ / 人工处理机制

**常见追问：**
- poison message 是什么？
- 死信队列的意义是什么？

### Q26：为什么选 Arq，而不是 Celery / Kafka / RabbitMQ？

**一句话结论：**
因为当前项目是 Python 全异步栈，任务复杂度不高，Arq 在“轻量 + async + Redis 复用”上最合适。

**展开 3 点：**
1. Arq 原生 async，和 FastAPI 技术栈契合
2. Celery 更成熟，但更重，异步适配也更绕
3. Kafka / RabbitMQ 是更底层的消息基础设施，不是当前规模下的第一选择

**常见追问：**
- 如果以后任务更复杂怎么办？
- 什么场景会考虑切到 Kafka？

## 七、认证与安全 高频题

### Q27：JWT 和 Session 怎么选？

**一句话结论：**
前后端分离、多实例扩展、移动端友好场景优先 JWT；需要强会话控制和即时吊销时 Session 更直接。

**展开 3 点：**
1. JWT 无状态，适合跨域和水平扩展
2. Session 有状态，服务端控制力更强
3. 项目选 JWT 是因为前后端分离、跨域、后续扩展更自然

**常见追问：**
- JWT payload 是加密的吗？
- SECRET 泄露会怎样？

### Q28：为什么密码要用 Argon2id？

**一句话结论：**
因为它是内存硬型密码哈希算法，更能抵抗 GPU/ASIC 暴力破解。

**展开 3 点：**
1. 比普通哈希和对称加密安全得多
2. 比 bcrypt 更现代，参数维度更丰富
3. 适合做密码存储，不适合做通用数据加密

**常见追问：**
- 为什么不能自己加盐然后 SHA256？
- bcrypt 和 Argon2id 的区别？

### Q29：当前项目的会话方案是什么？为什么还没上 Refresh Token？

**一句话结论：**
当前仓库实现的是 **access token + Redis 黑名单登出**；refresh token 是下一步完整会话治理方案，但不能讲成当前已上线能力。

**展开 3 点：**
1. 当前登录返回的是 access token，请求通过 `Authorization` 头传递，登出时把 token 哈希放进 Redis 黑名单
2. 这种方案已经能完成基本认证和登出，但会话治理还不够细，尤其缺少设备级续签和轮换能力
3. 如果后续升级，才会引入 refresh token、rotation、设备级撤销和全局失效策略

**常见追问：**
- 如果你来升级会怎么设计 refresh token？
- 黑名单该存 token 原文还是 hash？

### Q30：Prompt 注入为什么比 SQL 注入更难防？

**一句话结论：**
因为 SQL 注入有参数化查询这类银弹，而 Prompt 注入面对的是非确定性模型，没有 100% 防御方案。

**展开 3 点：**
1. SQL 注入针对确定性解析器
2. Prompt 注入针对自然语言模型，边界模糊
3. 只能做多层防御：输入检测、上下文检测、输出泄露检测、权限约束

**常见追问：**
- 为什么不能只靠 prompt 里写“忽略用户恶意输入”？
- 用户输入检测和上下文检测为什么要分开？

## 八、系统设计 高频题

### Q31：系统设计题开场第一步做什么？

**一句话结论：**
先澄清需求和非功能指标，再设计；不上来堆技术名词。

**展开 3 点：**
1. 功能需求：核心用户、核心路径、必须功能
2. 非功能需求：QPS、数据量、延迟、可用性、一致性、成本
3. 给默认假设，明确设计边界

**常见追问：**
- 如果面试官不给量级怎么办？
- 什么时候要做容量估算？

### Q32：高并发系统常用的 4 个套路是什么？

**一句话结论：**
缓存、异步化、削峰填谷、水平扩展，是最常见的 4 个基本套路。

**展开 3 点：**
1. 缓存解决读压力
2. 异步化和队列解决重任务与削峰
3. 水平扩展解决无状态服务吞吐，但不能代替数据层优化

**常见追问：**
- 什么时候该上分库分表？

### Q33：为什么不能一上来就分库分表？

**一句话结论：**
因为分库分表是高成本、难回滚的复杂度，只有单库瓶颈被证明确实存在时才值得上。

**展开 3 点：**
1. 先优化索引、SQL、缓存、异步化、热点拆分
2. 分片会显著增加事务、查询、迁移、运维复杂度
3. 小中型系统单库 PostgreSQL 往往还能走很远
