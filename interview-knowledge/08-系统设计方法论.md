# 系统设计方法论 — 从需求澄清到架构取舍

> 这篇不是讲某个框架 API，而是讲 **怎么回答系统设计题**。不会这个，你只能讲局部实现，讲不出架构判断。

---

## 一、系统设计题先做什么：不要急着画图

面试里最蠢的做法，就是用户刚说一句“设计一个聊天系统”，你立刻开始堆 Kafka、Redis、分库分表。那不是架构，那是条件反射。

系统设计第一步永远是：**澄清需求和约束**。

### 1.1 功能需求

先问清：
- 系统要解决什么问题？
- 核心用户是谁？
- 核心路径是什么？
- 哪些功能必须有，哪些是以后再说？

### 1.2 非功能需求

这是区分普通工程师和高阶工程师的关键：
- QPS / 并发连接数
- 数据规模
- 延迟目标（P95 / P99）
- 可用性目标
- 一致性要求
- 成本约束
- 安全/权限/合规要求

**一句硬话：** 不问非功能指标就开始设计，等于闭眼做架构。

### 1.3 先给默认假设

如果面试官不给数据，你要主动设边界：

- 日活 10 万还是 1000 万？
- 请求峰值 100 QPS 还是 10 万 QPS？
- 数据保留 7 天还是 5 年？
- 能不能接受最终一致？

架构从来不是抽象真理，而是约束下的取舍。

## 二、容量估算：不会算，就别谈高并发

### 2.1 为什么一定要估算

很多人一上来就说“加 Redis”“上 Kafka”“分库分表”，但连量级都不知道。你甚至不知道问题是不是值得这些复杂度。

### 2.2 一个最小估算模板

假设：
- DAU：10 万
- 峰值 QPS：平均 QPS × 3~10
- 平均请求大小：2KB
- 平均响应大小：8KB

那么：
- 平均 QPS = 日请求数 / 86400
- 峰值带宽 = 峰值 QPS × 平均包体
- 日增数据 = 日写入量 × 单条大小

**核心不是算得 100% 准，而是用估算决定是否需要复杂架构。**

### 2.3 面试里的正确姿势

你可以这样说：

> 如果系统当前只有几百 QPS，我默认优先用单库 + Redis + 异步任务，把简单方案做扎实；只有当单机数据库、单机 Redis、单队列 backlog 明确成为瓶颈时，我才会考虑分片、Kafka、Cluster 之类的复杂方案。

这就对了。架构的第一原则不是酷，是**成本和收益匹配**。

## 三、通用拆解框架：一套图讲大多数系统

大部分系统都能拆成这几层：

```text
Client
  -> Gateway / Nginx / LB
  -> API Service
  -> Cache / Queue / DB / Object Storage / Vector Store
  -> Observability
```

### 3.1 接入层
- 认证
- 限流
- TLS
- 路由
- 统一日志入口

### 3.2 服务层
- 业务编排
- 参数校验
- 状态机
- 幂等控制
- 降级逻辑

### 3.3 存储层
- PostgreSQL / MySQL：事务真相源
- Redis：缓存/锁/限流/短时状态
- 对象存储：图片/文件/大对象
- 向量库 / 搜索引擎：语义或全文检索

### 3.4 消息层
- 异步任务
- 解耦
- 削峰填谷
- 重试/补偿

### 3.5 观测层
- 日志
- 指标
- trace
- 告警

## 四、高并发设计常用套路

### 4.1 缓存

适合：
- 读多写少
- 热点数据
- 可以容忍短暂不一致

代价：
- 一致性复杂
- 热点治理
- 缓存穿透/击穿/雪崩

### 4.2 异步化

适合：
- 重任务
- 用户不需要同步拿结果
- 需要削峰填谷

代价：
- 状态跟踪复杂
- 重试/幂等/补偿复杂
- 最终一致而非强一致

### 4.3 削峰填谷

方式：
- 队列
- 批处理
- 限流
- 优先级

核心目的是：不要让下游在瞬时流量里被打死。

### 4.4 水平扩展

常见顺序：
1. 无状态服务多实例
2. 缓存与连接池优化
3. 数据库索引与查询优化
4. 异步化
5. 再考虑读写分离、分库分表、Cluster

不要倒着来。

## 五、一致性、可用性、幂等、重试、补偿

### 5.1 一致性 vs 可用性

不是所有系统都值得为强一致付高价。

- 账户余额、库存扣减：强一致更重要
- 缓存、推荐、统计：最终一致通常够用

### 5.2 幂等

幂等是重试的前提。

没有幂等保护的写接口，重试就是灾难制造机。

### 5.3 重试

只对临时性错误重试，而且必须有边界。

### 5.4 补偿

跨服务/跨资源时，经常做不到一个本地事务包到底，这时就要靠补偿：
- 回滚状态
- 反向操作
- 人工介入

系统越分布式，补偿越重要。

---

## 六、可观测性：没有观测，出了事全靠猜

至少要有：
- 请求成功率
- P95 / P99 延迟
- 数据库慢查询
- Redis 命中率
- 队列长度与 lag
- 错误率
- 关键后台任务成功率

记住：
- 日志回答“发生了什么”
- 指标回答“系统健康吗”
- trace 回答“慢在哪”

## 七、用本项目套 3 类系统设计题

### 7.1 题型一：设计一个 RAG 智能问答系统

**答题骨架：**
- 接入层：认证、限流、聊天接口
- 在线链路：query 预处理 -> 检索 -> rerank -> prompt -> LLM -> 流式返回
- 离线链路：上传 -> 解析 -> chunk -> embedding -> index
- 存储：PostgreSQL + PGVector + Redis + 对象/文件存储
- 风险：幻觉、脏数据、权限泄露、成本、延迟
- 优化：混合检索、缓存、增量重建、评测集、fallback 收口

### 7.2 题型二：设计一个异步任务处理平台

**答题骨架：**
- API 接入只负责创建任务与入队
- Worker 消费任务执行重操作
- PostgreSQL 记录任务真相状态
- Redis / MQ 负责队列和短时状态
- 关键点：幂等、重试、DLQ、超时、积压监控、优先级队列

### 7.3 题型三：设计一个文件上传 + 检索 + 权限系统

**答题骨架：**
- 上传走对象存储或本地持久化卷
- 元数据进 PostgreSQL
- 热点信息进 Redis
- 搜索分全文检索与语义检索
- 权限在查询入口和数据层双重校验
- 关键点：去重、版本、恢复、审计、容量治理

## 八、系统设计题的高频追问

### 8.1 瓶颈在哪？
你必须主动指出：
- 数据库
- Redis
- 外部模型 API
- 队列 backlog
- 带宽 / 大文件 I/O

### 8.2 怎么扩容？
要按顺序回答，而不是一上来分库分表。

### 8.3 怎么降级？
系统设计里不会谈降级，说明你只考虑了顺风，不考虑故障。

### 8.4 怎么回滚？
发布策略和 schema 兼容性，是很多候选人完全不会主动提的点。

---

## 九、面试里的常见错误

1. 不问约束，上来就堆技术名词
2. 不做估算，直接上“高并发架构”
3. 只谈功能，不谈可用性和成本
4. 只会“正常路径”，不会讲失败路径
5. 不知道什么时候该复杂，什么时候该保持简单

---

## 十、最后的答题原则

**先简单，再增强；先可验证，再扩展；先解决真实瓶颈，再引入复杂度。**

这是大厂和架构师真正看重的判断力。
