# 第一次真实 Baseline 结果与改进优先级

> 这份文档是对 `11-RAG最小评测与Baseline.md` 的第一次真实落地补充。  
> 它回答 3 个问题：  
> 1. 第一次 live baseline 到底跑出了什么结果  
> 2. 当前系统最值得先修什么  
> 3. 面试里应该怎么诚实地讲这次评测

---

## 0. 先给结论

第一次真实 baseline 已经跑通，当前结果可以概括成一句话：

**系统已经具备稳定的 RAG 主链路能力，但质量优化还停留在“关键词覆盖与知识点完整性”层面，尚未进入更精细的评测阶段。**

这句话很重要，因为它既不吹，也不矮化。

---

## 1. 本次真实评测的运行事实

评测脚本：

- `backend/evals/run_rag_eval.py`

评测数据：

- `backend/evals/rag_cases.json`

结果文件：

- `backend/evals/results/rag_eval_20260403_200035.json`

本次一共跑了 5 条 case，真实调用了：

- `/api/auth/login`
- `/api/chat/history`
- `/api/chat/stream`

也就是说，这不是 mock，也不是只测某个 service，而是一次真实系统 baseline。

## 2. 这次 baseline 的核心结果

### 2.1 总体指标

- 总 case 数：`5`
- 通过数：`5`
- 通过率：`100%`
- 平均得分：`92%`

这说明当前系统的最低结论不是“能不能用”，而是：

**已经能稳定回答，并且 route 基本合理，但仍有知识点覆盖不完整的问题。**

---

### 2.2 分 case 结果

#### `blade_crack_repair`

- route：`rag`
- score：`100%`
- source_count：`5`
- 结论：表现稳定，属于当前链路的强项问题

#### `corrosion_repair`

- route：`rag`
- score：`100%`
- source_count：`5`
- 结论：表现稳定，说明主知识库的典型维修类问题召回和生成都比较稳

#### `hide_craze_detection`

- route：`rag`
- score：`80%`
- 缺失关键词：`热像仪`
- 结论：系统知道隐裂要靠专业检测，也提到了热像检测，但没有明确覆盖到 case 指定的关键词表达

#### `thunderstrike_handling`

- route：`rag`
- score：`80%`
- 缺失关键词：`导雷系统`
- 结论：系统能回答“先停机并锁定叶轮”，但没有把雷击场景下的导雷系统检查明确讲出来

#### `greeting_capability`

- route：`fallback`
- score：`100%`
- source_count：`0`
- 结论：这条反而是个好信号，说明系统没有硬凹 RAG，而是把泛问候正确走到了 fallback

## 3. 当前系统最重要的结论，不是 100% pass

很多人看到 `100% pass` 会误判成“项目已经很成熟”。  
这是错误判断。

这次结果真正值钱的地方有两个：

1. **route 基本正确**

4 条知识库问题走 `rag`，1 条泛问候走 `fallback`。  
这说明 `rewrite -> retrieve -> rerank -> route` 这条主链目前没有明显跑偏。

2. **弱点已经开始具体化**

当前不是“整体不行”，而是：

- 某些专业知识点没有完整覆盖到回答中
- 回答能说对方向，但不一定把关键术语都讲全

这比“系统完全答偏”要好很多。  
因为这种问题通常属于：

- prompt 约束不够明确
- case 要求比当前生成策略更细
- 检索上下文中相关片段虽然被召回，但没被模型完整吸收进最终答案

---

## 4. 现在最该优先修的 2 个点

### P0-1：补“关键术语完整性”

当前最明显的缺口不是 route，也不是 source 不足，而是：

**答案方向对，但没有把关键术语讲全。**

这次暴露出来的两个代表词就是：

- `热像仪`
- `导雷系统`

这类问题的优先级高于继续扩 case 数。  
因为它直接影响你在面试里能不能说：

“系统目前的主要问题不是检索失败，而是专业知识点覆盖不完整。”

这是一句有工程判断力的话。

---

### P0-2：把评测从“通过”推进到“诊断”

当前评分规则已经够做 baseline，但还不够支持更细粒度优化。

现在的规则主要看：

- route 对不对
- 关键词有没有命中
- 是否命中禁用短语
- source 数量够不够
- 回答长度够不够

下一步更值钱的是补两个方向：

- `缺失关键词` 按主题分组
- `elapsed_ms` 纳入分析，判断质量和延迟之间有没有异常关系

换句话说：

**下一步不是先做更复杂的评测框架，而是先让现有 baseline 更能解释问题。**

---

## 5. 当前不该优先修什么

### 不优先修 1：多 Agent

这和当前问题没有关系。  
当前问题不是“单 Agent 不够强”，而是第一项目的 RAG 回答完整性还可继续优化。

### 不优先修 2：大规模观测平台

目前请求级日志、route、finish_reason、result file 都已经够支撑下一轮优化。  
现在上 Prometheus / OTel 不是第一优先级。

### 不优先修 3：继续疯狂扩 case

现在只扩 case，不修当前已经暴露出来的缺口，收益很低。  
应该先把当前 2 个代表性缺口修一轮，再继续扩。

---

## 6. 面试里怎么讲这次 baseline

推荐说法：

> 我给项目补了一套最小的 live eval，不是只测 service，而是真实登录后调用聊天流式接口，再结合聊天历史里的 route 和 sources 做规则评分。  
> 第一轮 baseline 跑了 5 条 case，平均分 92%，通过率 100%。  
> 当前最主要的问题不是 route 错，而是少数专业问题会漏掉关键术语，比如隐裂检测里的热像仪、雷击场景里的导雷系统。  
> 所以下一步我不会先扩架构，而是先做基于 case 的定向优化。

这段话的价值在于：

- 有真实系统证据
- 有评测方法
- 有当前结果
- 有明确下一步

这就是“工程化表达”。
