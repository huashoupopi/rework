# 聊天链路与最小可观测性 —— 重构版面试讲解

> 适用范围：这份文档专门重构第一项目里“聊天链路 / 流式接口 / 可观测性”这几块的面试讲法。  
> 它不是泛讲知识点，而是严格贴当前仓库真实实现。  
> 建议把它当成 `01-RAG-检索增强生成.md`、`07-FastAPI与后端架构.md`、`09-高频背诵版.md` 中相关内容的补充和校正版。

---

## 0. 先给结论

现在这套聊天系统可以这样准确描述：

**这是一个基于 FastAPI 的带认证流式聊天接口，入口做限流和用户级互斥，核心回答链路走 RAG 检索 / rerank / route / 流式生成，最近又补了一条最小请求级观测链，可以用 `request_id` 把一次请求从入口追到结束。**

这里最重要的是三个“不要讲错”：

1. **不要说这是标准 SSE。**  
   当前实现是 `fetch + ReadableStream + text/plain`，不是 `text/event-stream`。

2. **不要说已经有完整观测平台。**  
   当前是“请求级日志观测”刚补齐，不是完整的 metrics / tracing / 告警体系。

3. **不要把新加的 request_id 讲成全栈分布式 tracing。**  
   它是最小可用观测，不是 OpenTelemetry。

## 1. 当前仓库里的真实聊天链路

### 1.1 服务启动

入口在：

- `backend/app/main.py`

`lifespan` 启动时会做：

1. 初始化日志
2. 初始化数据库模型
3. 初始化 `RagService`
4. 初始化 Redis 连接池

这意味着聊天请求进入前，RAG 和 Redis 都应该已经准备好。

### 1.2 聊天路由入口

聊天接口在：

- `backend/app/routers/chat.py`

接口是：

- `POST /api/chat/stream`

它不是普通 JSON 接口，而是：

- 请求侧：`multipart/form-data`
- 响应侧：`StreamingResponse`
- `media_type="text/plain"`

这点一定要和标准 SSE 区分开。

### 1.3 路由层职责

`chat.py` 这一层不负责“想答案”，它主要负责：

1. 获取当前用户和数据库会话
2. 限流
3. Redis 分布式锁，避免同一用户并发发两条聊天
4. 图片上传与重编码
5. 写入用户消息
6. 拉最近会话窗口
7. 补任务图片检测结果
8. 决定是否给视觉模型传图
9. 调 `RagService.generate_chat_stream()`
10. 流结束后把 assistant 回答落库

所以面试里你应该把它描述为：

**聊天路由层是“请求编排层”，RAG 服务层才是“回答生成层”。**

### 1.4 RAG 服务职责

RAG 核心在：

- `backend/app/services/rag_service.py`

在线链路顺序是：

1. 输入安全检查
2. 多轮 query rewrite
3. 图片检测结果增强 query
4. hybrid retrieval
5. fallback 到纯向量检索
6. rerank
7. 上下文安全过滤
8. `rag / fallback` 路由决策
9. 构造 messages 或 vision prompt
10. 流式调用模型
11. 回传 sources

这条链最值得你背的 4 个词是：

- `rewrite`
- `retrieval`
- `rerank`
- `route`

## 2. 这次新增的最小可观测性

这次代码层做的不是“大观测平台”，而是**最小请求级观测链**。

### 2.1 新增了 `request_id` 上下文

新增文件：

- `backend/app/core/request_context.py`

核心能力：

1. 从请求头读取 `X-Request-ID`
2. 如果没有，就自动生成一个新的 request id
3. 把它写入 `request.state.request_id`
4. 把它放进 `ContextVar`
5. 在响应头回写 `X-Request-ID`

这意味着：

- 前端/测试脚本可以携带自己的 request id
- 后端所有链路日志可以自动带上同一个 request id
- 你以后排障时可以按一次请求聚合日志

### 2.2 用的是 ASGI 级 middleware，不是 BaseHTTPMiddleware

这一点很值钱，面试官如果细问，你可以直接讲。

为什么不用 `BaseHTTPMiddleware`：

1. 它对 streaming 场景和上下文传播不够稳
2. 你这条链是流式聊天，天然更适合 ASGI 级包裹
3. ASGI middleware 可以覆盖整个请求发送周期，更适合统计真实流式耗时

所以这次实现选择的是：

**手写 ASGI middleware + `ContextVar`，而不是简单的 `call_next` 风格日志中间件。**

### 2.3 日志现在能自动带 `request_id`

改动文件：

- `backend/app/core/logging.py`

做法不是给每条日志手传 `extra`，而是：

1. 在日志初始化时安装 `LogRecordFactory`
2. 统一给每条日志 record 注入 `request_id`
3. 日志格式中直接打印 `request_id=%(request_id)s`

这样做的好处是：

1. 对业务代码侵入小
2. `chat.py`、`rag_service.py`、`rate_limit.py` 这些模块不用一层层传参数
3. 同一次请求内的日志天然能串起来

### 2.4 请求层现在有统一开始/结束日志

中间件现在会产出两类基础日志：

- `http event=start`
- `http event=done`

它会记录：

- `method`
- `path`
- `status_code`
- `streaming`
- `response_start_ms`
- `total_ms`

这里有个很重要的工程点：

**因为这次是 ASGI 级 middleware，所以 `total_ms` 可以覆盖完整 streaming 生命周期。**

这和普通 `call_next` 风格 middleware 不一样。

### 2.5 聊天链路现在有业务开始/收尾日志

改动文件：

- `backend/app/routers/chat.py`
- `backend/app/services/rag_service.py`

新增了两类日志：

- `chat event=start`
- `chat event=done`

它们会记录：

- `user_id`
- `task_id`
- `question_len`
- `image_count`
- `finish_reason`
- `route`
- `sources`
- `response_len`
- `total_ms`

`finish_reason` 现在最少能区分：

- `ok`
- `timeout`
- `cancelled`
- `internal_error`
- `guardrail_blocked`
- `init_failed`

这就已经足够你在面试里说：

**我不是只打印日志，而是给聊天链做了最小生命周期观测，能区分一次请求是正常完成、超时、取消还是内部错误。**

## 3. 现在这套系统该怎么面试里讲

### 3.1 2 分钟版本

你可以这样讲：

> 我的聊天链路是一个带认证的流式接口。请求先经过 FastAPI 路由层，完成用户鉴权、限流、Redis 用户级互斥、图片处理、会话窗口拼接和任务图片上下文补充。然后进入 RAG 服务层，依次做 query rewrite、混合检索、rerank、上下文过滤和 rag/fallback 路由决策，最后再流式调用模型，把回答和来源返回给前端。  
>  
> 前端不是用标准 SSE，而是用 `fetch + ReadableStream` 去消费 `text/plain` 流。  
>  
> 最近我又给这条链补了一套最小请求级观测：通过 ASGI middleware 注入 `request_id`，并在日志层自动透传到聊天路由和 RAG 服务里。这样一次请求可以从入口日志、业务开始日志、RAG 阶段日志一直追到流结束日志，排障时能区分是正常结束、超时、取消还是内部错误。

### 3.2 一句话版本

**我做的不是“调一个模型接口”，而是一条带 RAG 路由、流式返回、用户级互斥和最小请求级观测的聊天链。**

## 4. 高频面试问题

### Q1：你这个聊天接口为什么不用 WebSocket？

**答：**

因为这个场景主要是服务端单向持续输出 token，不需要复杂双向实时协作。  
HTTP 流式已经能满足需求，而且和现有的 `multipart/form-data` 上传图片天然兼容，整体复杂度比 WebSocket 低。

### Q2：你这里是不是 SSE？

**答：**

不是标准 SSE。  
后端返回的是 `StreamingResponse(text/plain)`，前端用 `fetch + response.body.getReader()` 逐段消费。  
所以更准确的说法是：**HTTP 流式文本响应**。

### Q3：聊天路由层和 RAG 服务层怎么分工？

**答：**

路由层负责请求编排：鉴权、限流、加锁、图片处理、历史窗口、任务上下文。  
RAG 服务层负责回答生成：rewrite、retrieval、rerank、route、prompt/messages 构造和流式生成。  
这样分层更利于演进和排障。

### Q4：为什么要加 `request_id`？

**答：**

因为聊天链是跨多个阶段的：入口、限流、加锁、RAG 检索、模型流式生成、落库。  
如果没有统一 request id，日志只能零散地搜关键词，没法按一次请求完整重建。

### Q5：为什么不用 BaseHTTPMiddleware，而要自己写 ASGI middleware？

**答：**

因为这个项目有 streaming 场景，我想统计完整的流式生命周期，并保证请求上下文能稳定传到日志层。  
ASGI middleware 对 streaming 和上下文传播更稳，也更贴近底层请求生命周期。

### Q6：你现在的可观测性做到什么程度了？

**答：**

当前已经有：

1. `/health` 和 `/ready`
2. 请求级 `request_id`
3. 统一入口/出口日志
4. 聊天业务开始/结束日志
5. RAG 阶段日志

但还没有完整做到：

1. Prometheus 指标体系
2. OpenTelemetry 链路追踪
3. Sentry / 告警平台
4. 质量指标大盘

所以正确说法是：

**我已经把最小日志观测闭环补起来了，但完整平台化观测还没做完。**

### Q7：你怎么区分“能跑”和“可排障”？

**答：**

“能跑”只是接口有结果。  
“可排障”是指出了问题后能回答：

1. 是哪次请求
2. 谁发的
3. 走了哪条路由
4. 花了多久
5. 是正常结束、超时、取消还是内部错误

request_id 和 finish_reason 正是为这个目标服务的。

## 5. 你现在绝对不要吹的点

下面这些如果你讲成“已经完善上线能力”，会被追问死：

1. **不要说已经有完整 observability stack。**  
   现在主要还是日志观测，不是 metrics + tracing + alerting 全栈。

2. **不要说前端是 SSE。**  
   当前是 `fetch + ReadableStream`。

3. **不要说已经有完整 RAG eval。**  
   这块还是下一阶段重点。

4. **不要说 request_id 等于 trace_id。**  
   现在只是单服务内的请求关联 ID，不是完整分布式 trace。
