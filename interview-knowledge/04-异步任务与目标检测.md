## 一、异步编程基础

### 1.1 什么是异步编程？为什么需要？

**定义**：异步编程是一种编程范式，允许程序在等待 I/O 操作（网络请求、文件读写、数据库查询）完成时，不阻塞当前线程，而是去执行其他任务。当 I/O 操作完成后，程序会被通知并恢复执行。

**为什么需要**：

- **Web 服务的本质是 I/O 密集型**：一个 HTTP 请求的生命周期中，90% 以上的时间在等待——等数据库返回、等 Redis 响应、等文件读写。如果用同步模型，一个请求在等数据库时，整个线程就阻塞了，无法服务其他请求。
- **并发能力的根本区别**：同步模型下，1 个线程只能同时处理 1 个请求；异步模型下，1 个线程可以同时处理成百上千个请求（它们大部分时间都在等 I/O）。
- **资源效率**：线程切换有开销（上下文切换约 1-10 微秒），线程本身占内存（每个线程约 1-8MB 栈空间）。异步协程的切换开销极小，内存占用也极小。

**面试要点**：如果面试官问"你为什么选 FastAPI 而不是 Flask"，核心答案就是异步支持。FastAPI 原生基于 ASGI + asyncio，天然支持高并发 I/O 操作；Flask 是 WSGI 同步框架，处理并发需要依赖多线程/多进程。

### 1.2 Python asyncio 核心概念

#### 事件循环（Event Loop）

事件循环是 asyncio 的核心引擎，它是一个无限循环，不断地：
1. 检查哪些协程已经等够了（I/O 完成了）
2. 恢复这些协程的执行
3. 把新的等待注册到内核的 I/O 多路复用器（epoll/kqueue）

```
┌─────────────────────────────┐
│         Event Loop          │
│                             │
│  1. 检查就绪的 I/O 事件     │
│  2. 恢复对应的协程          │
│  3. 执行到下一个 await      │
│  4. 注册新的 I/O 等待       │
│  5. 回到步骤 1              │
│                             │
└─────────────────────────────┘
```

底层原理：
- Linux 使用 `epoll`，macOS 使用 `kqueue`，Windows 使用 `IOCP`
- 这些都是操作系统提供的 I/O 多路复用机制，允许一个线程同时监听多个文件描述符
- Python 的 asyncio 将这些系统调用封装成了统一的 API

#### 协程（Coroutine）

协程是可以被暂停和恢复的函数。用 `async def` 定义的函数返回的就是协程对象。

```python
async def fetch_data():
    # 这里遇到 await，协程会暂停，把控制权交还给事件循环
    result = await db.get(Task, task_id)
    # I/O 完成后，事件循环会恢复这个协程
    return result
```

**关键理解**：协程不是线程。协程是在同一个线程内通过协作式调度实现的并发。当一个协程 `await` 时，它主动让出控制权；事件循环不会"抢占"正在执行的协程。

#### 任务（Task）

Task 是对协程的封装，它将协程注册到事件循环中，使其开始执行。

```python
# 创建任务——协程开始被调度执行
task = asyncio.create_task(some_coroutine())
# 等待任务完成
result = await task
```

### 1.3 async/await 语法详解

```python
# async def 定义协程函数
async def run_yolo_detection(ctx: dict, task_id: int) -> dict:
    # await 暂停当前协程，等待异步操作完成
    async with AsyncSessionLocal() as db:
        task = await db.get(Task, task_id)  # 异步数据库查询
        # ...
        r = get_redis()
        await r.set(f"task:result:{task_id}", data, ex=3600)  # 异步 Redis 写入
```

**规则**：
- `await` 只能在 `async def` 函数内使用
- `await` 后面必须是一个 awaitable 对象（协程、Task、Future）
- 遇到 `await`，当前协程暂停，控制权回到事件循环
- `async with` 是异步上下文管理器，用于需要异步初始化/清理的资源
- `async for` 是异步迭代器，用于异步流式数据

### 1.4 异步 vs 多线程 vs 多进程

| 维度 | 异步（asyncio） | 多线程（threading） | 多进程（multiprocessing） |
|------|----------------|--------------------|-----------------------|
| **适用场景** | I/O 密集型 | I/O 密集型 | CPU 密集型 |
| **并发模型** | 单线程协作式 | 多线程抢占式 | 多进程 |
| **GIL 影响** | 不受 GIL 限制（因为本来就单线程） | 受 GIL 限制（CPU 密集时只能用一个核） | 不受 GIL 限制 |
| **内存开销** | 极低（协程约几 KB） | 中等（线程约 1-8MB） | 高（进程有独立内存空间） |
| **切换开销** | 极低（用户态切换） | 中等（内核态切换） | 高（进程切换） |
| **共享状态** | 天然安全（单线程） | 需要锁 | 需要 IPC（进程间通信） |
| **调试难度** | 低 | 高（竞态条件、死锁） | 中 |

**项目中的选择**：

- **Web 请求处理**：使用 asyncio（FastAPI）——因为 Web 请求本质是 I/O 密集型
- **YOLO 推理**：使用 `asyncio.to_thread()` 将 CPU 密集的推理放到线程池
- **Worker 进程**：使用 Arq Worker 独立进程——隔离 CPU 密集的推理任务，不影响 Web 服务

```python
# 项目中的经典用法：在异步函数中调用同步的 CPU 密集操作
result = await asyncio.to_thread(
    YOLOService.predict, task.original_path, task.result_path
)
```

`asyncio.to_thread()` 的原理：将同步函数提交到默认的 ThreadPoolExecutor，返回一个 awaitable。这样 CPU 密集的 YOLO 推理在线程池中执行，不阻塞事件循环。

## 二、任务队列

### 2.1 为什么需要任务队列？

**核心问题**：Web 请求有超时限制（通常 30-60 秒），但很多操作耗时远超这个限制。

```
用户上传图片 → API 接收 → YOLO 推理（5-30 秒）→ 返回结果
                              ↑
                         如果在这里卡住，
                         用户看到的是 502/504 超时
```

**任务队列解决的问题**：
1. **解耦请求和处理**：API 只负责接收请求、入队，立即返回；Worker 进程异步处理
2. **超时保护**：请求不会因为耗时操作而超时
3. **重试机制**：任务失败可以自动重试
4. **并发控制**：控制同时执行的任务数量，保护资源（GPU 显存、CPU）
5. **可观测性**：任务有明确的状态流转，可以查看队列长度、处理速度等

### 2.2 生产者-消费者模式

任务队列的本质是生产者-消费者模式：

```
┌───────────┐    任务入队    ┌───────────┐    任务出队    ┌───────────┐
│  API 进程  │ ─────────→  │   Redis    │ ─────────→  │  Worker   │
│ (生产者)   │             │  (队列)    │             │ (消费者)   │
└───────────┘              └───────────┘              └───────────┘
     │                          │                          │
     │ 1. 接收HTTP请求          │ 2. 存储任务              │ 3. 取出任务
     │ 2. 创建DB记录            │    (FIFO队列)            │ 4. 执行推理
     │ 3. 任务入队              │                          │ 5. 更新DB/缓存
     │ 4. 立即返回响应          │                          │ 6. 失败则重试
```

项目中的实现：

```python
# 生产者（API 进程） - task.py
job = await arq.enqueue_job(
    "run_yolo_detection",  # 任务函数名
    new_task.id,           # 任务参数
    _job_id=f"yolo_{new_task.id}",  # 任务唯一ID，防止重复入队
)

# 消费者（Worker 进程） - worker.py + yolo_task.py
class WorkerSettings:
    functions = [run_yolo_detection, run_knowledge_rebuild]
```

### 2.3 常见任务队列对比

| 维度 | Celery | Arq | RQ（Redis Queue） |
|------|--------|-----|-------------------|
| **语言** | Python | Python | Python |
| **异步支持** | 部分（4.x 引入） | 原生 async | 不支持 |
| **消息队列** | Redis/RabbitMQ/SQS | 仅 Redis | 仅 Redis |
| **复杂度** | 高（功能全面） | 低（轻量级） | 低 |
| **性能** | 中等 | 高 | 中等 |
| **定时任务** | Beat 调度器 | 内置 cron | 需额外库 |
| **监控** | Flower（Web UI） | 简单 | rq-dashboard |
| **社区** | 最大 | 较小 | 中等 |

**为什么选 Arq？**

1. **原生异步**：项目全栈异步（FastAPI + asyncpg + aioredis），Arq 原生异步，无缝集成
2. **轻量**：Celery 太重，RQ 不支持异步，Arq 是最佳平衡
3. **基于 Redis**：项目已经用 Redis 做缓存和限流，不需要额外引入 RabbitMQ
4. **内置重试**：自带指数退避重试，不需要额外配置

### 2.4 Arq（Async Redis Queue）详解

#### 架构原理

Arq 使用 Redis 的 List 和 Sorted Set 作为底层队列：

```
Redis 内部数据结构：
┌─────────────────────────────────────────┐
│ arq:queue:default  (List)               │ ← 待执行的任务
│   [task_data_json_1, task_data_json_2]  │
├─────────────────────────────────────────┤
│ arq:job:yolo_123   (Hash)               │ ← 单个任务的详细信息
│   function: run_yolo_detection          │
│   args: [123]                           │
│   status: queued/in_progress/complete   │
│   result: {...}                         │
├─────────────────────────────────────────┤
│ arq:result:yolo_123 (String)            │ ← 任务结果
│   {"task_id": 123, "status": "done"}    │
└─────────────────────────────────────────┘
```

Worker 进程启动后：
1. 连接 Redis
2. 用 `BLPOP` 阻塞式地从队列中取任务（没有任务时 Worker 阻塞等待，不消耗 CPU）
3. 执行任务函数
4. 将结果写回 Redis
5. 如果失败且配置了重试，按指数退避重新入队

#### WorkerSettings 配置详解

```python
class WorkerSettings:
    # ===== 任务注册 =====
    functions = [run_yolo_detection, run_knowledge_rebuild]
    # Worker 只执行这里注册的函数，未注册的任务会被忽略
    # 这是一种白名单机制，防止恶意任务被执行

    # ===== Redis 连接 =====
    redis_settings = parse_redis_settings()
    # Arq 使用自己的 RedisSettings 类，不是 redis-py 的连接
    # Worker 和 API 连接同一个 Redis 实例

    # ===== 并发控制 =====
    max_jobs = 4
    # 同时最多执行 4 个任务
    # 设置依据：
    # - CPU 核数和 GPU 显存是硬约束
    # - YOLO 推理是 CPU/GPU 密集型，并发太高会 OOM
    # - 建议：GPU 推理设 2，CPU 推理设 4-8

    # ===== 超时控制 =====
    job_timeout = 120  # 秒
    # 单个任务的最大执行时间
    # 超时后任务会被强制终止，状态标记为 timeout
    # 设置依据：YOLO 推理通常 5-30 秒，120 秒足够留余量

    # ===== 重试配置 =====
    retry_jobs = True
    max_tries = 3
    # 重试间隔是指数退避：~10s → ~30s → ~90s

    # ===== 生命周期钩子 =====
    on_startup = on_startup    # Worker 启动时执行（加载模型）
    on_shutdown = on_shutdown   # Worker 关闭时执行（清理资源）
```

#### 任务注册和调度

**任务函数的签名规则**：

```python
async def run_yolo_detection(ctx: dict, task_id: int) -> dict:
    """
    第一个参数必须是 ctx（Arq 上下文）
    后面的参数是入队时传入的参数
    返回值会被序列化存入 Redis
    """
```

`ctx` 字典包含：
- `ctx['redis']`：Arq Redis 连接实例
- `ctx['job_id']`：当前任务的 ID
- `ctx['job_try']`：当前是第几次尝试（从 1 开始）

**入队方式**：

```python
# 基本入队
job = await arq.enqueue_job("run_yolo_detection", task_id)

# 带自定义 job_id（防止重复入队）
job = await arq.enqueue_job(
    "run_yolo_detection",
    new_task.id,
    _job_id=f"yolo_{new_task.id}",  # 相同 job_id 的任务不会重复入队
)

# 延迟执行
job = await arq.enqueue_job("cleanup", _defer_by=timedelta(hours=1))

# 定时执行（cron）
cron_jobs = [
    cron(cleanup_expired_files, hour=3, minute=0),  # 每天凌晨 3 点
]
```

#### 重试机制与指数退避

**什么是指数退避（Exponential Backoff）？**

当任务失败时，不是立即重试，而是等待越来越长的时间后再重试：

```
第 1 次失败 → 等待 ~10 秒 → 第 1 次重试
第 2 次失败 → 等待 ~30 秒 → 第 2 次重试
第 3 次失败 → 等待 ~90 秒 → 第 3 次重试（max_tries=3，之后放弃）
```

**为什么需要指数退避？**

1. **避免雪崩**：如果 100 个任务同时失败（比如 GPU OOM），立即重试会导致 100 个任务同时再次尝试，加剧问题
2. **等待资源恢复**：GPU 显存被释放、文件系统恢复、网络恢复——这些都需要时间
3. **减少无效重试**：如果是暂时性故障（偶发 OOM），等一会儿就好了；如果是永久性故障（模型文件损坏），3 次重试后放弃也是合理的

**项目中重试的实现关键**：

```python
# yolo_task.py
except Exception:
    task.status = TaskStatus.FAILED.value
    await db.commit()
    # 关键：抛出异常 → Arq 会自动重试
    # 如果不抛出异常 → Arq 认为任务成功，不会重试
    raise
```

注意这里有一个微妙的设计：先将任务状态更新为 FAILED，然后 raise。Arq 捕获异常后会自动安排重试，重试时任务函数会重新执行，会再次将状态更新为相应的值。

#### 任务超时处理

```python
job_timeout = 120  # 秒
```

当任务执行超过 120 秒：
1. Arq 会取消该任务的协程（抛出 `asyncio.CancelledError`）
2. 任务被标记为超时失败
3. 如果配置了重试，会按指数退避重试

**设置超时的原则**：
- 太短：正常推理还没完成就被杀了
- 太长：卡死的任务占用资源太久
- 经验值：正常推理时间的 3-5 倍

## 三、YOLO 目标检测

### 3.1 什么是目标检测？

目标检测是计算机视觉的核心任务之一，目标是在一张图像中同时完成两件事：
1. **定位**：找到目标物体的位置（用边界框 Bounding Box 表示）
2. **分类**：识别每个目标物体属于哪个类别

```
输入：一张图片
输出：
  [
    {"class": "corrosion", "confidence": 0.92, "box": [100.0, 200.0, 300.0, 400.0]},
    {"class": "craze",     "confidence": 0.87, "box": [150.0, 250.0, 350.0, 450.0]}
  ]

  box 格式为 [x1, y1, x2, y2]：左上角坐标和右下角坐标
```

### 3.2 YOLO 的核心思想

**YOLO = You Only Look Once**

传统目标检测方法（如 R-CNN 系列）是"两阶段"的：
1. 第一阶段：生成候选区域（Region Proposals）——可能有几千个
2. 第二阶段：对每个候选区域分类

YOLO 的革命性在于"一阶段"：
- 将整张图像划分为 S×S 的网格
- 每个网格同时预测边界框和类别概率
- 一次前向传播就完成检测，速度极快

```
传统方法：生成候选区域(慢) → 逐个分类(慢) → 合并结果
YOLO：    整图一次推理(快) → NMS 后处理(快) → 结果
```

### 3.3 YOLO 版本演进

| 版本 | 年份 | 关键改进 | 特点 |
|------|------|---------|------|
| **YOLOv1** | 2016 | 开创一阶段检测 | 速度快但精度有限 |
| **YOLOv2** | 2017 | Batch Norm、Anchor Box | 精度大幅提升 |
| **YOLOv3** | 2018 | 多尺度预测、残差网络 | 平衡速度和精度 |
| **YOLOv4** | 2020 | CSP 主干网络、Mosaic 增强 | 性能进一步提升 |
| **YOLOv5** | 2020 | PyTorch 实现、易用性极高 | Ultralytics 出品 |
| **YOLOv8** | 2023 | Anchor-free、解耦头 | 当前主流 |
| **YOLOv11** | 2024 | C3k2 模块、大核卷积注意力 | 最新，更高精度 |

**项目使用的是 Ultralytics 框架**（支持 YOLOv5/v8/v11），通过 `ultralytics` Python 包：

```python
from ultralytics import YOLO
model = YOLO("best.pt")  # 加载训练好的模型权重
```

### 3.4 YOLOv11 架构特点

YOLOv11（YOLO11）的关键改进：

1. **C3k2 模块**：使用更小的卷积核组合替代大卷积核，减少参数量的同时保持感受野
2. **SPPF（Spatial Pyramid Pooling Fast）**：空间金字塔池化的快速版本，提取多尺度特征
3. **C2PSA（Cross Stage Partial with Spatial Attention）**：引入空间注意力机制，让模型更关注重要区域
4. **解耦检测头**：分类和回归使用独立的分支，提高精度

### 3.5 推理流程详解

```
图像输入 → 预处理 → 模型推理 → NMS 后处理 → 结果解析
```

#### 1) 图像预处理

```python
# Ultralytics 内部自动完成：
# 1. 读取图像（BGR 格式，OpenCV 默认）
# 2. Letterbox 缩放到 640x640（保持宽高比，填充灰色边框）
# 3. BGR → RGB 转换
# 4. HWC → CHW 转置（Height-Width-Channel → Channel-Height-Width）
# 5. 归一化到 [0, 1]
# 6. 添加 batch 维度：(3, 640, 640) → (1, 3, 640, 640)
```

#### 2) 模型推理

```python
results = cls.model(
    source=image_path,  # 输入图像路径
    conf=0.25,          # 置信度阈值
    iou=0.45,           # NMS 的 IoU 阈值
    save=False,         # 不自动保存结果
    verbose=False,      # 不打印日志
)
```

#### 3) NMS（非极大值抑制）

**为什么需要 NMS？**

模型对同一个物体可能产生多个重叠的检测框。NMS 的作用是去除冗余的检测框，只保留最好的那个。

**NMS 算法步骤**：

```
1. 按置信度对所有检测框降序排序
2. 取置信度最高的框作为基准
3. 计算其他所有框与基准框的 IoU
4. 删除 IoU > 阈值（0.45）的框（认为它们检测的是同一个物体）
5. 从剩余的框中取置信度最高的，重复步骤 2-4
6. 直到没有剩余的框
```

#### 4) 置信度阈值（Confidence Threshold）

```python
conf=0.25  # 置信度阈值
```

- 置信度 = 模型对"这里有一个物体"以及"这个物体属于某个类别"的综合确信程度
- `conf=0.25` 意味着只保留置信度 > 25% 的检测结果
- **阈值太高**（如 0.8）：漏检率高，可能错过真实目标
- **阈值太低**（如 0.1）：误检率高，会检测出很多不存在的目标
- **0.25 是工业默认值**，在精度和召回率之间取得平衡

#### 5) IoU（交并比）

**IoU = 交集面积 / 并集面积**

```
    ┌─────────────┐
    │    框 A     │
    │    ┌────────┼──────┐
    │    │ 交集   │      │
    └────┼────────┘      │
         │      框 B     │
         └───────────────┘

IoU = 交集面积 / (框A面积 + 框B面积 - 交集面积)
```

- IoU = 0：完全不重叠
- IoU = 1：完全重合
- `iou=0.45`：两个框重叠超过 45% 就认为检测的是同一个物体

#### 6) 结果后处理

```python
# 项目中的结果解析 - yolo_service.py

plotted = result.plot(line_width=2, font_size=1.0)  # 在原图上绘制检测框
cv2.imwrite(save_path, plotted)  # 保存结果图像

for box in result.boxes:
    cls_id = int(box.cls[0])           # 类别 ID
    detect_data["objects"].append({
        "class": result.names[cls_id],                        # 类别名称
        "confidence": round(float(box.conf[0]), 4),           # 置信度

    })
```

## 四、模型加载模式

### 4.1 单例模式（Singleton）

**为什么模型加载要用单例？**

YOLO 模型文件通常有几十到几百 MB，加载到内存需要数秒甚至十几秒。如果每个请求都重新加载模型：
- 内存浪费：多个模型实例占用大量内存
- 时间浪费：每次加载都要从磁盘读取并初始化
- GPU 显存溢出：多个模型实例挤爆显存

项目中的单例实现：

```python
class YOLOService:
    model = None  # 类变量，所有实例共享

    @classmethod
    def load_model(cls) -> None:
        if cls.model is not None:  # 已加载，直接返回
            return
        model_path = settings.YOLO_MODEL_PATH
        model_file = Path(model_path)
        if not model_file.exists():
            raise FileNotFoundError(f"YOLO 模型文件不存在: {model_path}")
        cls.model = YOLO(model_path)
        # 预热
        cls.model(np.zeros((640, 640, 3), dtype=np.uint8), verbose=False)

    @classmethod
    def predict(cls, image_path: str, save_path: str) -> dict:
        if cls.model is None:
            cls.load_model()  # 懒加载：第一次使用时才加载
        # ...推理逻辑
```

这个实现使用了**类变量 + classmethod** 的方式实现单例，而不是传统的 `__new__` 或元类方式。这更 Pythonic，也更适合无状态的工具类。

### 4.2 冷启动 vs 热启动

| | 冷启动 | 热启动 |
|---|--------|--------|
| **定义** | 模型还没加载到内存 | 模型已经在内存中 |
| **耗时** | 5-30 秒（读磁盘 + 初始化 + 分配 GPU 显存） | 几乎为 0 |
| **触发条件** | Worker 刚启动、进程重启、OOM 被杀后重启 | Worker 已经在运行 |

**项目的策略**：通过 `on_startup` 钩子在 Worker 启动时就加载模型，避免第一个请求的冷启动延迟。

```python
async def on_startup(ctx: dict) -> None:
    YOLOService.load_model()  # Worker 启动时立即加载模型
```

### 4.3 模型预热（Warm-up）

```python
cls.model(np.zeros((640, 640, 3), dtype=np.uint8), verbose=False)
```

**为什么要预热？**

1. **CUDA 初始化**：GPU 推理需要首次编译 CUDA kernel，这个过程很慢（可能几秒）
2. **内存分配**：第一次推理会触发 GPU 显存分配、内存映射
3. **JIT 编译**：一些框架（如 TensorRT）会在第一次推理时进行图优化
4. **CPU 缓存预热**：将模型参数加载到 CPU 缓存中

**预热方法**：用一个全零的假图像做一次推理。这次推理的结果没有意义，但它触发了所有的初始化过程。之后的真实推理就不会有冷启动延迟了。

### 4.4 YOLO 模式选择（CPU vs GPU）

```python
# Ultralytics 会自动检测：
# 1. 如果有 NVIDIA GPU + CUDA → 用 GPU
# 2. 如果有 Apple Silicon + MPS → 用 MPS
# 3. 否则 → 用 CPU
```

| 模式 | 推理速度 | 适用场景 |
|------|---------|---------|
| GPU (CUDA) | 最快（5-20ms/图） | 有 NVIDIA 显卡的服务器 |
| MPS (Apple Silicon) | 中等（20-50ms/图） | macOS 开发机 |
| CPU | 最慢（100-500ms/图） | 无 GPU 的环境 |

项目中的并发配置也要根据硬件调整：

```python
max_jobs = 4
# 小参数模型（如 qwen3.5:4b）→ 可以 4-8 并发
# 标准 YOLO 模型 → 建议 2 并发（GPU 显存限制）
# 大模型 → 建议 1-2 并发
```

### 4.5 项目中的模型加载实现总结

```
Worker 启动
    │
    ├─ on_startup() 被调用
    │   └─ YOLOService.load_model()
    │       ├─ 检查 cls.model is not None → 已加载则跳过（单例保护）
    │       ├─ 检查模型文件是否存在
    │       ├─ YOLO(model_path) → 加载模型权重
    │       └─ model(zeros_image) → 预热
    │
    ├─ 监听 Redis 队列
    │
    └─ 接收到任务
        └─ YOLOService.predict()
            ├─ cls.model is None? → load_model()（双重保护/懒加载）
            ├─ model(image, conf=0.25, iou=0.45)
            ├─ result.plot() → 绘制检测框
            └─ 返回检测数据
```

### 5.3 EXIF 信息处理

**什么是 EXIF？**

EXIF（Exchangeable Image File Format）是嵌入在 JPEG/PNG 等图片中的元数据，包含：
- 拍摄时间、相机型号、镜头参数
- **GPS 位置信息**（经纬度）
- 拍摄者信息
- 图像方向（旋转信息）

**为什么要剥离 EXIF？**

1. **隐私问题**：GPS 信息泄露拍摄地点，这在工业场景中尤其敏感（暴露设备位置）
2. **安全问题**：EXIF 可以包含恶意数据（某些 EXIF 解析器有漏洞）
3. **方向问题**：如果不处理 EXIF 中的方向信息，图片可能显示为旋转的

项目中 YOLO 框架（Ultralytics）内部会自动处理 EXIF 方向信息，确保图片以正确的方向进行推理。

## 六、分布式锁

### 6.1 为什么需要分布式锁？

在分布式系统（或多进程系统）中，多个进程/服务可能同时操作同一个资源，需要互斥机制来保证数据一致性。

**项目中的场景**：用户快速双击上传按钮，可能触发两次相同文件的上传请求。如果不加锁，同一张图片会被处理两次，浪费计算资源。

### 6.2 Redis SET NX EX 实现分布式锁

```python
# task.py
file_hash = hashlib.md5(content).hexdigest()
lock_key = f"lock:upload:{current_user.id}:{file_hash}"

# SET NX EX 是原子操作
acquired = await r.set(lock_key, "1", nx=True, ex=30)
if not acquired:
    raise HTTPException(status_code=409, detail=f"文件{file.filename}正在处理中，请勿重复提交")
```

**参数详解**：

- `nx=True`（Not eXists）：只有当 key 不存在时才设置成功。如果 key 已存在，返回 False
- `ex=30`（Expire）：设置过期时间为 30 秒。30 秒后自动删除 key（自动释放锁）
- 整个操作是**原子的**：检查 + 设置在一条 Redis 命令中完成，不会有竞态条件

**Lock Key 的设计**：

```
lock:upload:{user_id}:{file_hash}
```

- `lock:upload`：锁的命名空间，区分不同类型的锁
- `{user_id}`：用户隔离，不同用户上传同一文件不冲突
- `{file_hash}`：文件内容的 MD5 哈希，精确到文件内容级别

### 6.3 锁的过期时间设置

```python
ex=30  # 30 秒过期
```

**为什么是 30 秒？**

- 太短（如 5 秒）：正常处理还没完成，锁就过期了，第二个请求又进来了
- 太长（如 10 分钟）：如果进程崩溃导致锁没有释放，要等 10 分钟才能再次上传同一文件
- 30 秒是合理的：覆盖了从上传到入队的时间（通常几秒），同时不会因为进程崩溃而长时间阻塞

### 6.4 防止死锁

**死锁场景**：如果使用 `SETNX` 不带过期时间——

```
1. 进程 A 获取锁
2. 进程 A 崩溃（没有释放锁）
3. 锁永远存在 → 所有后续请求都被拒绝 → 死锁
```

**解决方案**：使用 `SET NX EX`，锁带有过期时间。即使进程崩溃，锁也会在 30 秒后自动释放。

**注意**：更复杂的场景（如需要延长锁持有时间）可以用 Redlock 算法或看门狗机制（Watchdog）。但项目中的场景比较简单，SET NX EX 就够用了。

### 6.5 项目中的分布式锁应用场景总结

| 场景 | Key 模式 | 过期时间 | 目的 |
|------|---------|---------|------|
| 防重复上传 | `lock:upload:{user_id}:{file_hash}` | 30s | 同一用户同一文件不重复处理 |

## 七、并发控制

### 7.1 信号量（Semaphore）的概念

信号量是一种并发控制原语，用于限制同时访问某个资源的并发数。

```
Semaphore(2) 表示最多同时有 2 个协程进入临界区

协程 A → 获取 (计数: 2→1) → 进入 → 释放 (计数: 1→2)
协程 B → 获取 (计数: 1→0) → 进入 → 释放 (计数: 0→1)
协程 C → 获取 (计数: 0) → 阻塞等待...
         ↑ 当 A 或 B 释放后，C 才能进入
```

### 7.2 asyncio.Semaphore 的使用

项目中 RAG 服务使用信号量控制并发：

```python
# rag_service.py
class RagService:
    _chat_sema = asyncio.Semaphore(settings.RAG_MAX_CONCURRENCY)  # 默认为 2

    @classmethod
    async def generate_chat_stream(cls, ...):
        async with cls._chat_sema:  # 获取信号量，超过并发数则等待
            async with asyncio.timeout(settings.RAG_STREAM_TOTAL_TIMEOUT_S):
                # ... 执行 RAG 推理
```

### 7.3 为什么需要限制并发数？

1. **GPU/CPU 资源有限**：LLM 推理和 YOLO 推理都很消耗资源，并发太高会 OOM
2. **外部服务限流**：Ollama / LM Studio 有自己的并发限制
3. **服务稳定性**：宁可让请求排队等待，也不要让服务崩溃
4. **公平性**：防止一个用户的大量请求占用所有资源

### 7.4 项目中的并发控制实现

项目中有两层并发控制：

**第一层：Arq Worker 的 max_jobs**

```python
class WorkerSettings:
    max_jobs = 4  # Worker 同时最多执行 4 个任务
```

这控制的是 Worker 进程级别的并发。Worker 从 Redis 队列中取任务时，如果正在执行的任务数已经达到 4，就不会再取新任务。

**第二层：RAG 服务的 Semaphore**

```python
_chat_sema = asyncio.Semaphore(settings.RAG_MAX_CONCURRENCY)  # 默认为 2
```

这控制的是 API 进程内 RAG 推理的并发。即使有 100 个用户同时发起 chat 请求，也只有 2 个在同时推理。

**第三层：限流（Rate Limiting）**

```python
await rate_limit(current_user.id, "upload", limit=20, window=60)
```

这控制的是用户级别的请求频率（见下文第六节）。

## 八、两级缓存策略

### 8.1 为什么需要缓存？

数据库查询有网络延迟（1-10ms）和查询开销。对于频繁读取的数据，缓存可以将延迟降低到微秒级。

项目中的场景：用户上传图片后，会反复刷新页面查看检测结果。如果每次都查数据库，数据库压力大。

### 8.2 项目中的缓存实现

项目实现了 **Redis 缓存**作为读缓存层：

```python
# task.py - get_task_detail
async def get_task_detail(task_id: int, ...):
    r = get_redis()

    # 第一层：查 Redis 缓存
    cached = await r.get(f"task:result:{task_id}")
    if cached:
        data = json.loads(cached)
        # 注意：缓存中必须存 user_id，用于权限校验
        if data.get("user_id") != current_user.id and not current_user.is_superuser:
            raise HTTPException(status_code=404, detail="任务不存在")
        return data  # 缓存命中，直接返回

    # 第二层：缓存未命中，查数据库
    task = await db.get(Task, task_id)
    if not task:
        raise HTTPException(status_code=404, detail="任务不存在")

    # 回填缓存（只缓存已完成的任务）
    if task.status == TaskStatus.COMPLETED.value:
        await r.set(
            f"task:result:{task_id}",
            json.dumps({...}),
            ex=3600,  # TTL: 1 小时
        )
    return task
```

同时在 Worker 任务完成时也会主动写入缓存：

```python
# yolo_task.py - run_yolo_detection
r = get_redis()
await r.set(
    f"task:result:{task_id}",
    json.dumps({
        "id": task_id,
        "user_id": task.user_id,
        "status": TaskStatus.COMPLETED.value,
        "detect_result": result,
    }),
    ex=3600,  # TTL: 1 小时
)
```

### 8.3 TTL（Time To Live）设置

```python
ex=3600  # 1 小时过期
```

**为什么设 1 小时？**

- 任务结果是不可变的（检测完成后不会再变），理论上可以缓存很久
- 但缓存占用 Redis 内存，不常访问的结果应该被清理
- 1 小时覆盖了用户的典型使用周期（上传 → 查看结果 → 离开）

### 8.4 缓存失效策略

项目使用的是 **TTL 被动过期**：
- 每条缓存设置 1 小时的 TTL
- 过期后 Redis 自动删除
- 下次查询时缓存未命中，从数据库重新加载

**缓存一致性保证**：
- 只缓存 COMPLETED 状态的任务结果（不可变数据）
- 不缓存 PROGRESSING 或 FAILED 状态的任务（可能变化）
- 这避免了缓存和数据库不一致的问题

**潜在问题——缓存穿透**：
- 如果用户查询一个不存在的 task_id，每次都会穿透缓存打到数据库
- 解决方案：可以缓存空结果（`"null"`），设置较短的 TTL（如 60 秒）
- 项目中通过用户权限校验（只能查自己的任务）间接降低了穿透风险

### 8.5 缓存安全注意事项

```python
# 缓存中必须存 user_id，读缓存时要校验
if data.get("user_id") != current_user.id and not current_user.is_superuser:
    raise HTTPException(status_code=404, detail="任务不存在")
```

这是一个容易被忽略的安全问题：缓存绕过了数据库的权限查询，但不能绕过权限校验。缓存中必须包含权限相关的字段（如 `user_id`），读取时必须校验。

## 九、数据库操作

### 9.1 任务状态流转

```
PENDING → PROGRESSING → COMPLETED
                      ↘ FAILED (可重试) → PROGRESSING → COMPLETED
```

状态定义：

```python
class TaskStatus(Enum):
    PENDING = "pending"          # 已创建，等待处理
    PROGRESSING = "progressing"  # 正在处理中
    COMPLETED = "completed"      # 处理完成
    FAILED = "failed"            # 处理失败
```

状态流转时机：

| 状态变化 | 触发时机 | 触发位置 |
|---------|---------|---------|
| → PROGRESSING | 任务创建时 | `task.py` upload_tasks |
| → COMPLETED | 推理成功 | `yolo_task.py` run_yolo_detection |
| → FAILED | 推理失败 | `yolo_task.py` run_yolo_detection |
| FAILED → PROGRESSING | Arq 自动重试时 | 由重试逻辑驱动 |

项目中创建任务时直接设为 PROGRESSING 而不是 PENDING，因为入队和开始执行之间的间隔很短，PENDING 状态实际上没有被使用。

### 9.2 乐观更新 vs 悲观锁

**悲观锁**：操作前先加锁，防止其他事务修改。
```sql
SELECT * FROM tasks WHERE id = 1 FOR UPDATE;  -- 加行锁
UPDATE tasks SET status = 'completed' WHERE id = 1;
COMMIT;
```

**乐观更新**：不加锁，直接更新，但用版本号或条件检查确保数据没有被其他事务修改。
```sql
UPDATE tasks SET status = 'completed' WHERE id = 1 AND status = 'progressing';
-- 如果 affected_rows = 0，说明已被其他事务修改
```

**项目中的实现**：

```python
# yolo_task.py - 乐观检查
if task.status == TaskStatus.COMPLETED.value:
    logger.info("任务已完成，跳过 task_id=%d", task_id)
    return {"task_id": task_id, "status": "already_completed"}
```

项目使用了简单的"检查后更新"模式。由于每个任务只有一个 Worker 在处理（通过 Arq 的 job_id 去重保证），不存在并发更新的问题，所以不需要悲观锁。

### 9.3 游标分页（Cursor Pagination）vs 偏移分页（Offset Pagination）

#### 偏移分页（Offset Pagination）

```sql
SELECT * FROM tasks ORDER BY created_at DESC OFFSET 20 LIMIT 10;
```

**优点**：简单，可以直接跳到任意页
**缺点**：
- OFFSET 大时性能差（数据库需要扫描前 N 行再丢弃）
- 并发插入时会出现数据重复或遗漏

项目中的实现：

```python
# crud/task.py
stmt = (
    base_stmt.options(selectinload(Task.owner))
    .order_by(Task.created_at.desc())
    .offset(skip)
    .limit(limit)
)
```

#### 游标分页（Cursor Pagination）

```sql
SELECT * FROM tasks WHERE created_at < '2024-01-01 12:00:00'
ORDER BY created_at DESC LIMIT 10;
```

**优点**：
- 性能稳定：使用索引，不需要扫描前 N 行
- 数据一致：不会因为并发插入而出现重复/遗漏

**缺点**：
- 不能跳到任意页
- 实现稍复杂

**项目为什么用偏移分页？**

- 数据量较小（个人用户的任务数量有限）
- 前端需要"第 X 页"的跳转功能
- 简单场景下偏移分页完全够用

**面试加分**：如果数据量大（如百万级），应该切换到游标分页。

### 9.4 项目中的分页实现

```python
async def get_tasks_paginated(
    db: AsyncSession, user_id: int, is_superuser: bool, skip: int = 0, limit: int = 10
) -> TaskPaginationSchema:
    # 1. 构建基础查询（含权限过滤）
    base_stmt = select(Task)
    if not is_superuser:
        base_stmt = base_stmt.where(Task.user_id == user_id)

    # 2. 计算总数（复用 base_stmt，保证一致性）
    total_stmt = select(func.count()).select_from(base_stmt.subquery())
    total = (await db.execute(total_stmt)).scalar_one()

    # 3. 分页查询
    stmt = (
        base_stmt.options(selectinload(Task.owner))  # 预加载关联用户
        .order_by(Task.created_at.desc())             # 最新的在前面
        .offset(skip)
        .limit(limit)
    )
    result = (await db.execute(stmt)).scalars().all()

    return TaskPaginationSchema(total=total, items=[...])
```

**关键设计**：
- `subquery()` 将 base_stmt 包装为子查询，count 直接复用过滤条件，避免了列表数据和总数不一致的问题
- `selectinload(Task.owner)` 预加载关联的用户数据，避免 N+1 查询问题

### 9.5 异步数据库操作

项目使用 SQLAlchemy 2.0 的异步模式：

```python
# database.py
engine = create_async_engine(settings.DATABASE_URL, echo=settings.DB_ECHO)
AsyncSessionLocal = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
```

**`expire_on_commit=False` 的含义**：

默认情况下，SQLAlchemy 在 `commit()` 后会标记所有对象为"过期"，下次访问属性时会触发数据库查询（lazy loading）。但在异步模式下，lazy loading 会触发同步 I/O，导致错误。设置 `expire_on_commit=False` 后，commit 后对象的属性仍然可以直接访问，不会触发额外查询。

**Worker 中的数据库连接**：

```python
# yolo_task.py
async with AsyncSessionLocal() as db:
    task = await db.get(Task, task_id)
    # ...
```

Worker 进程直接使用 `AsyncSessionLocal()`，不经过 FastAPI 的依赖注入（`Depends(get_db)`）。因为 Worker 不是 HTTP 请求上下文，没有 FastAPI 的生命周期管理。

## 十、限流（Rate Limiting）

### 10.1 固定窗口算法

项目使用**固定窗口限流算法**：

```python
async def rate_limit(user_id: int, endpoint: str, limit: int = 10, window: int = 60) -> None:
    r = get_redis()
    key = f"ratelimit:{user_id}:{endpoint}"

    # INCR 是原子操作：key 不存在则创建并设为 1，存在则 +1
    current = await r.incr(key)
    if current == 1:
        await r.expire(key, window)  # 第一次请求时设置窗口过期时间

    if current > limit:
        raise HTTPException(status_code=429, detail=f"请求过于频繁，请{window} 秒后再试")
```

**工作原理**：

```
时间窗口 [0s ─────────── 60s]
请求计数: 1, 2, 3, ... 20, 21(拒绝!), 22(拒绝!)...
                              ↑
                         limit=20 到达上限

60 秒后 key 过期，计数重置为 0
```

**固定窗口的边界问题**：

```
窗口 1: [0:00 - 1:00]  最后 1 秒内来了 20 个请求 ✓
窗口 2: [1:00 - 2:00]  前 1 秒内又来了 20 个请求 ✓

实际上在 [0:59 - 1:01] 这 2 秒内来了 40 个请求！超过了预期的限流效果。
```

这是固定窗口算法的已知问题。更精确的做法是使用**滑动窗口**（Sliding Window Log / Counter），但固定窗口实现简单，对于项目场景已经足够。

## 十一、任务系统可靠性与工程设计

### 11.1 at-least-once 是现实，exactly-once 往往是宣传语

任务系统最容易被面试官追问的，不是“你用的是 Arq 还是 Celery”，而是**投递语义**。

大多数业务队列能真正做到的是 **at-least-once（至少一次）**：
- 任务不会轻易丢
- 但可能执行多次

为什么？因为在“执行成功”与“确认成功”之间，只要任一环节抖一下，就可能重复投递。

典型场景：
1. Worker 已经完成数据库写入
2. 还没来得及 ack
3. 进程崩了 / 网络断了
4. 队列认为任务没完成 → 重新投递

这时如果你的任务不是幂等的，就会产生重复副作用。

**exactly-once** 在工程里极难成立，通常要依赖：
- 幂等写入
- 去重键
- 事务消息/外部协调
- 极高的实现复杂度

所以成熟答案不是“我们做到 exactly-once”，而是：
**我们接受 at-least-once，并通过幂等设计把重复执行的副作用消掉。**

### 11.2 幂等键、任务状态机与去重窗口

#### 幂等键（Idempotency Key）

任务提交时应该尽量有一个能唯一代表业务动作的键，例如：
- 上传文件：`user_id + file_hash`
- 知识库重建：`dataset_id + version`
- 支付任务：`order_id`

这样即使客户端重试、网关重试、worker 重投，也能判断“这是不是同一件事”。

#### 状态机约束

任务系统不要只有一个 `status` 字符串，还要有**合法流转边界**：

```text
PENDING -> QUEUED -> RUNNING -> COMPLETED
                    \-> FAILED -> RETRYING -> RUNNING
```

关键点：
- 不能从 `COMPLETED` 回到 `RUNNING`
- 不能无限制重试
- 重试次数、最后错误、开始时间、结束时间最好都留痕

#### 去重窗口

去重不是永远去重，而是“在一段业务相关时间内去重”。

例如上传防重：30 秒内同一文件重复提交直接拒绝，很合理；永久去重反而会伤害正常业务。

### 11.3 什么错误该重试，什么错误绝不能重试

这是可靠性设计的基本功。

**适合重试的错误：**
- 短暂网络抖动
- Redis / PostgreSQL / 外部 API 的瞬时超时
- 临时资源争抢（短暂锁冲突）
- 目标服务 502/503

**不适合重试的错误：**
- 参数非法
- 文件格式错误
- 权限不足
- 业务状态不满足
- 代码 bug 导致的确定性异常

如果对所有异常都无脑重试，只会把错误放大成雪崩。

### 11.4 指数退避、poison message 与死信队列（DLQ）

#### 指数退避

重试间隔应该递增，而不是 1 秒一把梭：
- 第 1 次：10s
- 第 2 次：30s
- 第 3 次：90s

这样做是为了避免：
- 下游刚恢复前又被冲垮
- 同类失败任务一起集中回灌

#### Poison Message

有些任务不是“暂时失败”，而是“这条任务本身就有毒”：
- 数据坏了
- 依赖字段缺失
- 版本不兼容
- 代码路径必然抛错

这种任务如果反复重试，只是在浪费资源。

#### 死信队列（DLQ）

当任务超过最大重试次数后，应该进入 DLQ 或“人工处理池”，而不是悄悄丢掉。

DLQ 的意义：
- 留痕
- 排查
- 人工回放
- 统计某类任务持续失败的趋势

### 11.5 队列积压、扩缩容与削峰填谷

任务系统不是“能跑就行”，而是要考虑 backlog。

你至少要监控：
- 队列长度
- 平均等待时间（queue lag）
- 任务执行耗时
- 重试率
- 最终失败率

**扩容策略：**
- Worker 增实例
- 单实例并发数调大
- 重任务与轻任务分队列
- 按优先级分流

**但注意**：
- Worker 不是越多越好
- 下游（数据库、Redis、GPU、模型服务）可能先被打爆
- 扩 worker 之前要先确认瓶颈在哪

### 11.6 Arq vs Celery vs RabbitMQ vs Kafka

把这些东西混成一类，会被面试官直接看穿。

| 组件 | 本质定位 | 强项 | 代价 |
|------|----------|------|------|
| Arq | Python 异步任务队列 | 轻量、原生 async、适合 FastAPI 技术栈 | 生态和复杂工作流能力不如 Celery |
| Celery | Python 通用任务框架 | 功能成熟、生态完善、任务编排更多 | 配置更重、异步栈适配更绕 |
| RabbitMQ | 消息队列 Broker | ACK、路由、优先级、DLQ 成熟 | 需要额外运维、吞吐不主打极限 |
| Kafka | 分布式日志系统 / 事件流平台 | 高吞吐、可回放、顺序分区、数据保留 | 运维复杂、并不适合所有业务任务 |

**本项目为什么选 Arq：**
- 全栈 async
- 任务模型不复杂
- Redis 已经是基础设施
- 不想为当前规模引入 RabbitMQ/Kafka 的额外复杂度

但如果未来要做：
- 更复杂的工作流编排
- 任务优先级 / DLQ / 回放体系更重
- 多语言消费者
- 大规模事件流

那就要重新评估 Celery / RabbitMQ / Kafka。

## 十二、面试高频问题

### Q1: 你的项目中为什么需要异步任务队列？直接在 API 中处理不行吗？

**参考答案**：

不行，主要有三个原因：

1. **超时问题**：YOLO 推理需要 5-30 秒，如果在 API 请求中同步处理，Nginx/负载均衡器可能在 30-60 秒后超时断连，用户会看到 502/504 错误。

2. **资源隔离**：YOLO 推理是 CPU/GPU 密集型操作，如果在 API 进程中执行，会阻塞事件循环（即使用 `asyncio.to_thread()`，也会占用线程池），影响其他用户的 HTTP 请求响应。使用独立的 Worker 进程，API 进程只做 I/O 操作，保持高响应性。

3. **可靠性**：任务队列提供重试机制。GPU 显存偶尔被占用导致 OOM，重试一次就能成功。如果在 API 中直接处理，失败了用户就要重新上传。

### Q2: 为什么选择 Arq 而不是 Celery？

**参考答案**：

项目全栈异步（FastAPI + asyncpg + aioredis），Arq 是原生异步的任务队列，与技术栈无缝集成。Celery 虽然功能更全面（支持 RabbitMQ、Canvas 工作流等），但它本质是同步架构，在异步项目中使用需要额外的适配层。而且 Celery 的依赖更重，配置更复杂。对于我们的场景（YOLO 推理 + 知识库重建），Arq 的功能完全够用，轻量且性能好。

### Q3: 解释一下你项目中的分布式锁是怎么实现的？

**参考答案**：

使用 Redis 的 `SET key value NX EX 30` 命令实现。NX 表示 key 不存在时才能设置成功（原子操作），EX 30 设置 30 秒过期时间防止死锁。

具体场景是防止重复上传：用户双击上传按钮，两个请求几乎同时到达。第一个请求 SET NX 成功，获取锁；第二个请求 SET NX 失败，返回 409 Conflict。锁的 key 是 `lock:upload:{user_id}:{file_hash}`，用文件内容的 MD5 来识别相同文件。

### Q4: YOLO 的 NMS（非极大值抑制）是什么？为什么需要？

**参考答案**：

NMS 用于去除同一个物体的重复检测框。YOLO 在推理时，同一个物体可能会被多个网格单元检测到，产生多个高度重叠的边界框。NMS 的算法是：按置信度降序排序所有检测框；取最高置信度的框为基准；计算其他框与它的 IoU（交并比）；删除 IoU 超过阈值（如 0.45）的框；对剩余框重复此过程。最终每个物体只保留一个最佳检测框。

### Q5: 为什么模型加载要用单例模式？

**参考答案**：

YOLO 模型权重文件有几十到几百 MB，加载到内存需要数秒，还要分配 GPU 显存。如果每个推理请求都重新加载模型，不仅浪费时间和内存，GPU 显存也会溢出。单例模式确保整个 Worker 进程中只有一份模型实例，所有推理请求共享同一个模型，实现资源的高效利用。

项目中用类变量 `model = None` + `@classmethod` 实现单例：第一次调用 `load_model()` 时加载并赋值给类变量，后续调用检查 `cls.model is not None` 直接返回。

### Q6: 什么是模型预热（Warm-up）？为什么需要？

**参考答案**：

模型预热是在模型加载后、正式服务前，用一个假数据做一次推理。目的是触发所有一次性的初始化操作：CUDA kernel 编译、GPU 显存分配、CPU 缓存加载等。如果不预热，第一个真实请求会承受冷启动延迟（可能多出几秒），影响用户体验。

项目中用一个 640x640 的全零矩阵做预热：
```python
cls.model(np.zeros((640, 640, 3), dtype=np.uint8), verbose=False)
```

### Q7: asyncio.to_thread() 的作用是什么？什么时候用？

**参考答案**：

`asyncio.to_thread()` 将一个同步阻塞函数提交到线程池执行，返回一个 awaitable 对象。用于在异步代码中调用无法异步化的同步阻塞操作，避免阻塞事件循环。

项目中 YOLO 推理使用 OpenCV 和 PyTorch，这些是同步 CPU 密集型操作，无法用 async/await 改写。所以用 `asyncio.to_thread()` 放到线程池：

```python
result = await asyncio.to_thread(YOLOService.predict, task.original_path, task.result_path)
```

使用场景总结：
- 调用同步阻塞的第三方库（如 OpenCV、PIL、PyTorch CPU 推理）
- 文件系统的同步操作（如大文件读写）
- 任何无法异步化的 CPU 密集型操作

### Q8: 你的缓存策略是什么？如何保证缓存一致性？

**参考答案**：

项目使用 Redis 作为读缓存层，策略是 **Cache-Aside（旁路缓存）**：

- **读路径**：先查 Redis 缓存，命中直接返回；未命中查数据库，然后回填缓存（TTL 1 小时）
- **写路径**：Worker 完成推理后，同时更新数据库和写入缓存

一致性保证：只缓存 COMPLETED 状态的任务结果。任务结果是不可变数据（检测完成后不会再变），所以不存在缓存和数据库不一致的问题。PROGRESSING 和 FAILED 状态的任务不缓存，每次都查数据库。

安全注意事项：缓存中包含 `user_id` 字段，读取缓存时必须校验权限，防止用户通过猜测 task_id 访问其他用户的数据。

### Q9: 解释一下你项目中的限流实现

**参考答案**：

使用 Redis 实现固定窗口限流算法。Key 为 `ratelimit:{user_id}:{endpoint}`，每次请求用 `INCR` 原子递增计数，第一次请求时用 `EXPIRE` 设置窗口过期时间。如果计数超过限制（如 20次/分钟），返回 HTTP 429。

`INCR` 是 Redis 原子操作，即使高并发也不会出现竞态条件。key 设计包含 `user_id` 和 `endpoint`，实现了用户级别、接口级别的细粒度限流。

固定窗口的已知问题是窗口边界处可能出现双倍峰值，更精确的做法是滑动窗口，但固定窗口实现简单，对于项目场景已经足够。

### Q10: Worker 进程和 API 进程的关系是什么？

**参考答案**：

它们是完全独立的进程，有各自的内存空间。通过 Redis 队列进行通信。

- **API 进程**：运行 FastAPI 应用，处理 HTTP 请求，将任务入队到 Redis
- **Worker 进程**：运行 Arq Worker，从 Redis 队列取任务并执行（YOLO 推理、知识库重建）

API 进程不加载 YOLO 模型（节省内存），Worker 进程不处理 HTTP 请求。两者通过共享的 PostgreSQL 数据库和 Redis 缓存交换数据。

启动方式也不同：
- API：`uvicorn app.main:app`
- Worker：`arq app.worker.WorkerSettings`

### Q11: 你项目中的 Redis 连接池是怎么管理的？

**参考答案**：

项目维护两个独立的 Redis 连接：

1. **Arq Redis 连接**（`_arq_pool`）：专门用于任务入队，使用 Arq 的 `create_pool()` 创建
2. **通用 Redis 连接池**（`_redis_pool`）：用于缓存、限流、分布式锁，使用 `redis.ConnectionPool.from_url()` 创建，配置了 `max_connections=10`

在 FastAPI 的 lifespan 中初始化和关闭：
- 启动时：`init_redis()` 创建连接池
- 关闭时：`close_redis()` 释放连接池

为什么用连接池：每次操作新建 TCP 连接需要 1-3ms 的建连开销，高频操作累积开销巨大。连接池复用已有连接，0 开销。

### Q12: 任务失败后的重试机制是怎么工作的？

**参考答案**：

Arq 内置了重试机制：

1. 任务函数抛出异常 → Arq 捕获异常
2. 检查当前尝试次数是否 < `max_tries`（配置为 3）
3. 如果可以重试 → 按指数退避计算等待时间（~10s, ~30s, ~90s）→ 重新入队
4. 如果已达最大重试次数 → 标记任务为最终失败

关键代码：
```python
except Exception:
    task.status = TaskStatus.FAILED.value
    await db.commit()
    raise  # 必须抛出异常，Arq 才会重试
```

如果捕获异常后不 raise，Arq 认为任务成功完成，不会重试。这是一个容易犯的错误。

### Q13: 解释 IoU（交并比）和它在目标检测中的作用

**参考答案**：

IoU（Intersection over Union）是衡量两个边界框重叠程度的指标：

$$IoU = \frac{交集面积}{并集面积}$$

- IoU = 0：完全不重叠
- IoU = 1：完全重合
- 通常 IoU > 0.5 就认为检测到了正确的目标

在目标检测中 IoU 有两个用途：
1. **NMS 阶段**：IoU 超过阈值（如 0.45）的检测框被认为是同一个物体的重复检测，被抑制
2. **评估阶段**：用 IoU 判断预测框和真实框是否匹配，计算 mAP（平均精度均值）

项目中设置 `iou=0.45`，意味着两个框重叠超过 45% 就认为是同一个物体。

### Q14: 你的文件上传为什么要用 UUID 命名？

**参考答案**：

三个原因：

1. **防冲突**：多个用户可能上传同名文件（如 `photo.jpg`），UUID 保证全局唯一
2. **安全**：防止路径遍历攻击。如果用原始文件名，攻击者可能上传名为 `../../etc/passwd` 的文件
3. **隐私**：原始文件名可能包含敏感信息（如 `张三的风机检测报告.jpg`）

UUID v4 基于随机数生成，碰撞概率极低（约 $2^{-122}$），可以认为全局唯一。

### Q15: 你如何保证任务不会被重复处理？

**参考答案**：

三层防护：

1. **分布式锁**：上传时用 `SET NX` 锁住 `{user_id}:{file_hash}`，同一用户同一文件 30 秒内不能重复上传
2. **Arq job_id 去重**：入队时设置 `_job_id=f"yolo_{task_id}"`，相同 job_id 的任务不会重复入队
3. **任务状态检查**：Worker 执行前检查任务是否已完成：
```python
if task.status == TaskStatus.COMPLETED.value:
    return {"task_id": task_id, "status": "already_completed"}
```

### Q16: 异步编程中的 async with 是什么？

**参考答案**：

`async with` 是异步上下文管理器，等同于同步的 `with` 语句，但支持异步的进入和退出操作。

对象需要实现 `__aenter__()` 和 `__aexit__()` 方法。

项目中的使用场景：

```python
# 数据库会话管理
async with AsyncSessionLocal() as db:
    task = await db.get(Task, task_id)

# 信号量控制并发
async with cls._chat_sema:
    # 获取信号量后执行

# 超时控制
async with asyncio.timeout(120):
    # 超过 120 秒自动取消
```

### Q17: 你的项目中有哪些并发控制手段？

**参考答案**：

四层并发控制：

1. **限流（Rate Limiting）**：用户级别，每分钟最多 20 次上传。基于 Redis INCR + EXPIRE 实现固定窗口算法
2. **分布式锁**：请求级别，同一用户同一文件不能重复上传。基于 Redis SET NX EX 实现
3. **Worker max_jobs**：进程级别，Worker 同时最多执行 4 个任务。由 Arq 内部控制
4. **Semaphore**：协程级别，RAG 推理最多 2 个并发。使用 `asyncio.Semaphore` 实现

### Q18: 为什么 Worker 中用 AsyncSessionLocal() 而不是 Depends(get_db)？

**参考答案**：

`Depends(get_db)` 是 FastAPI 的依赖注入机制，只在 HTTP 请求上下文中可用。Worker 进程不处理 HTTP 请求，没有 FastAPI 的请求生命周期，所以不能用 `Depends`。

Worker 直接使用 `AsyncSessionLocal()` 创建数据库会话：

```python
async with AsyncSessionLocal() as db:
    task = await db.get(Task, task_id)
```

这是一个上下文管理器，确保会话在使用完后自动关闭。

### Q19: 你的知识库重建任务是怎么实现的？

**参考答案**：

知识库重建作为 Arq 异步任务实现，支持两种模式：
- **full**（全量重建）：重建整个知识库索引
- **incremental**（增量重建）：只重建指定文档的索引

实现方式比较特别——使用 `asyncio.create_subprocess_exec()` 启动子进程执行 `build_knowledge.py` 脚本：

```python
process = await asyncio.create_subprocess_exec(
    *cmd, cwd=str(BACKEND_DIR), env=env,
    stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE,
)
stdout, stderr = await asyncio.wait_for(process.communicate(), timeout=timeout)
```

为什么用子进程而不是直接在 Worker 中执行？因为知识库重建涉及大量的库导入（LlamaIndex、PyTorch 等），这些库可能与 Worker 进程的其他任务冲突。使用子进程实现了完全的隔离。

同时设置了超时控制（`KNOWLEDGE_BUILD_TIMEOUT_S = 600` 秒），超时后会 `process.kill()` 强制终止子进程。

### Q20: 你的项目如何处理任务结果的权限校验？

**参考答案**：

权限校验贯穿了整个查询链路：

1. **数据库查询**：分页查询时，非超级管理员只能查看自己的任务
   ```python
   if not is_superuser:
       base_stmt = base_stmt.where(Task.user_id == user_id)
   ```

2. **缓存读取**：缓存中包含 `user_id`，读取时必须校验
   ```python
   if data.get("user_id") != current_user.id and not current_user.is_superuser:
       raise HTTPException(status_code=404, detail="任务不存在")
   ```

3. **文件下载**：下载结果图片前校验任务归属
   ```python
   if not current_user.is_superuser and task.user_id != current_user.id:
       raise HTTPException(status_code=403, detail="没有权限访问此任务")
   ```

注意一个安全细节：权限不足时返回 404 而不是 403，避免泄露"这个任务存在但你没权限"的信息（信息泄露漏洞）。
