## 0. 先给结论

一个 RAG 项目如果你只能讲 happy path，面试官很快就会判断你只会“跑通”，不会“扛系统”。

这条聊天链真正值钱的地方，不只是：

- 能检索
- 能流式输出
- 能返回 sources

而是你知道它最常见会怎么挂，以及挂了以后你先看哪里。

**这才是“工程感”的核心。**

---

## 1. 当前聊天链的故障面到底分几层

如果把这条链拆开，它的故障面大概分 6 层：

1. **请求入口层**  
   参数不合法、限流、并发冲突、认证失败

2. **安全防护层**  
   用户输入被阻断、输入被净化、上下文节点被剔除

3. **检索路由层**  
   改写失败、检索空结果、top_score 太低、误走 fallback

4. **模型生成层**  
   初始化失败、上游 LLM 异常、超时、空输出

5. **流式传输层**  
   客户端断开、重复输出、think 残留、sources 拼接异常

6. **落库与会话层**  
   assistant 消息没存上、meta 不完整、历史窗口污染

面试里不要把这些全混成一句“可能网络有问题”。  
要像工程师一样讲：

**我会先判断问题落在哪一层，再看对应的日志和信号。**

## 2. 最值得背的 10 个失败模式

下面这 10 个，是你现在最应该熟悉的。

### 2.1 空问题被拒绝

**现象：**

- 接口直接返回 400
- 用户看起来像“发不出去”

**真实信号：**

- `chat event=bad_request ... reason=empty_question`

**根因：**

- 路由层在进入后续逻辑前就做了 `question.strip()` 判空

**怎么查：**

先看请求级日志和 `chat event=bad_request`。  
这种问题不用看 RAG 日志，因为根本没进 RAG。

**面试怎么讲：**

这是典型的入口校验失败，不属于模型问题，也不属于检索问题。

---

### 2.2 被限流

**现象：**

- 接口返回 429
- 用户觉得“突然不能问了”

**真实信号：**

- `限流触发 user_id=... endpoint=chat_stream count=...`

**根因：**

- Redis 固定窗口限流命中

**怎么查：**

先看请求状态码，再看 Redis 限流日志。  
不要误判成登录失效或模型挂了。

**面试怎么讲：**

限流是入口层治理，不是业务层错误。  
它的目标是保护系统，不是修复回答质量。

---

### 2.3 用户级并发冲突

**现象：**

- 接口返回 409
- 用户连续发两条消息时，第二条被拒绝

**真实信号：**

- `chat event=lock_conflict user_id=...`

**根因：**

- Redis `SET NX EX` 用户锁没拿到

**怎么查：**

先看 409，再看 lock 日志。  
如果同一个用户上一条还在生成，这是预期保护行为，不是 bug。

**面试怎么讲：**

这是为了避免同一用户多条流式聊天并发，把会话状态和资源消耗搞乱。

---

### 2.4 图片上传失败

**现象：**

- 400
- 带图聊天失败，但纯文本聊天正常

**常见原因：**

1. 图片类型不支持
2. 图片超过大小限制
3. 图像重编码失败

**怎么查：**

先区分是纯文本请求还是图片请求。  
这类问题优先看路由层和文件处理，不要第一时间去查模型。

**面试怎么讲：**

图片链路是聊天链的一个分支故障面，它和文本 RAG 不是同一类问题。

---

### 2.5 用户输入被 guardrail 阻断

**现象：**

- 用户拿到固定拒答
- 业务日志里没有正常的回答链路

**真实信号：**

- `用户输入过长被阻断`
- `用户输入被阻断 score=... rules=...`
- 最终 `finish_reason=guardrail_blocked`

**根因：**

- 输入长度过长
- 或 prompt 注入评分超过阻断阈值

**怎么查：**

先看安全日志，再看 `chat event=done finish_reason=guardrail_blocked`。  
不要误以为是“模型不懂这个问题”。

**面试怎么讲：**

这说明系统不是“所有输入都 blindly 喂给模型”，而是在最前面做了安全收口。

---

### 2.6 Query rewrite 失败或效果不佳

**现象：**

- 多轮追问突然答偏
- 像“那这个呢”“那隐裂呢”这种问题表现不稳定

**真实信号：**

- `rag stage=rewrite ...`
- 或 `rag rewrite 失败，回退原始 query`
- 或 `rag rewrite 结果异常，回退原始 query`

**根因：**

- rewrite 接口调用失败
- 改写结果异常
- 或本来就不该 rewrite，但启发式判断不够完美

**怎么查：**

看 rewrite 日志，再对照原问题和 rewritten query。  
这是检索前的问题，不是 rerank 问题。

**面试怎么讲：**

多轮 RAG 的关键风险之一就是指代消解失败。  
rewrite 不是锦上添花，而是多轮可用性的关键点。

---

### 2.7 检索空结果或弱结果，误走 fallback

**现象：**

- 用户问的是知识库里应该能答的问题，但系统给出泛化回答
- sources 很少或没有

**真实信号：**

- `Hybrid search返回0结果，降级为纯向量检索`
- `rag stage=route route=fallback ... top_score=...`

**根因：**

1. hybrid retrieval 没召回
2. top_score 太低
3. 上下文节点数量不够

**怎么查：**

先看：

1. `rag stage=retriever`
2. `rag stage=route`
3. `top_score`
4. `node` 数量

这是最典型的“看起来模型答错，实际上是检索没拿到足够上下文”。

**面试怎么讲：**

RAG 的核心瓶颈很多时候不在生成，而在检索和路由。

---

### 2.8 上下文节点被安全规则剔除过多

**现象：**

- 明明检索到了内容，但最后上下文仍然很弱
- route 或回答质量突然下降

**真实信号：**

- `上下文节点被剔除 score=... rules=...`
- `剔除可疑上下文节点 score=... snippet=...`

**根因：**

- 某些 chunk 被当作可疑上下文剔除
- 结果是可用节点数下降

**怎么查：**

不要只看检索命中了多少个节点，还要看**最后剩了多少个安全节点**。  
这是“召回成功 ≠ 最终可用”的典型例子。

**面试怎么讲：**

安全治理不是零成本的，它会直接影响可用上下文质量，所以要同时看安全和召回效果。

---

### 2.9 模型超时或上游异常

**现象：**

- 用户长时间等待后失败
- 最终出现统一错误提示

**真实信号：**

- `rag stage=timeout`
- `RAG 生成失败`
- `finish_reason=timeout`
- `finish_reason=internal_error`

**根因：**

- 上游模型响应太慢
- 网络波动
- 视觉链路更重
- provider 报错

**怎么查：**

先看 `finish_reason`，再看：

1. `rag stage=ttfb`
2. `rag stage=done`
3. 是否走了 vision

如果连 `ttfb` 都没有，说明问题更可能在模型请求发起前或刚发起时。  
如果 `ttfb` 有了但总耗时爆炸，通常是生成过程拖太久。

**面试怎么讲：**

流式系统排障时，我会区分“首 token 慢”和“总生成慢”，这两个问题的根因不一样。

---

### 2.10 客户端中途断开

**现象：**

- 用户刷新页面或断网
- 后端流没完全走完

**真实信号：**

- `客户端断开，保存已生成内容 len=...`
- `rag stage=cancelled`
- `finish_reason=cancelled`

**根因：**

- 客户端主动取消请求
- 网络断开

**怎么查：**

这类问题不要误判成服务端异常。  
如果有 `cancelled`，通常是连接被取消而不是系统内部报错。

**面试怎么讲：**

流式接口里，“取消”是正常失败模式，不应该和“内部错误”混为一类。

## 3. 当前最实用的排障顺序

如果你现在真要查一次问题，顺序应该是：

### 第一步：先看请求层

看：

- `http event=start`
- `http event=done`
- `request_id`
- `status_code`

先确认：

1. 请求到底有没有进来
2. 是 4xx、5xx 还是 200
3. 是不是 streaming 请求

### 第二步：再看聊天业务层

看：

- `chat event=start`
- `chat event=done`
- `finish_reason`

先判断：

1. 有没有进聊天主链
2. 最终是 `ok`、`timeout`、`cancelled` 还是 `internal_error`

### 第三步：再看 RAG 阶段层

看：

- rewrite
- retriever
- route
- ttfb
- done

核心判断：

1. query 有没有改写
2. 检索节点数够不够
3. route 是 `rag` 还是 `fallback`
4. 是否有 sources

### 第四步：最后才看安全与上下文污染

看：

- 用户输入阻断/净化
- 上下文节点剔除
- 是否有输出泄露告警

这一步通常不是第一眼先看，但一旦发现“为什么突然 route 变差 / 回答变弱”，就必须查。

## 4. 现在这条链最值得讲的工程认知

### 4.1 不要把所有失败都归到模型

一个成熟的回答应该能区分：

1. 入口失败
2. 安全阻断
3. 检索问题
4. 路由问题
5. 模型超时
6. 流式取消

这比“模型有时候不稳定”强太多。

### 4.2 `fallback` 不是一定坏事

`fallback` 有两种情况：

1. 用户问候、闲聊，本来就应该 fallback
2. 知识库命中题误走 fallback，这才是问题

所以不要一看到 fallback 就说系统坏了。  
要结合问题类型判断。

### 4.3 取消和错误必须分开讲

`cancelled` 是连接生命周期问题。  
`internal_error` 才是服务端真正出错。  
这两个如果混着讲，面试官会立刻看出你没处理过流式系统。

## 5. 面试里怎么讲“失败画像”

### 5.1 1 分钟版本

你可以这样讲：

> 我在这个项目里比较重视失败模式的拆分。聊天链不是单点逻辑，而是入口治理、RAG 检索、模型生成、流式传输和会话落库串起来的。所以我不会把所有问题都归结成“模型不稳定”。比如 429 是限流问题，409 是用户级并发锁冲突；guardrail_blocked 是安全阻断；route=fallback 往往说明上下文质量不够；timeout 和 cancelled 也要分开看。这样排障时会先按 request_id 看请求层和聊天收尾日志，再下钻到 RAG 的 rewrite、retriever、route 和 ttfb 信号。面试里我也会把这条链讲成一个有失败画像的系统，而不是只有 happy path。

### 5.2 一句话版本

**我不仅知道它怎么跑，还知道它最容易怎么挂、挂了先查哪里。**

## 6. 高频面试问题

### Q1：你怎么定位“回答变差”到底是检索问题还是模型问题？

**答：**

我会先看 route 和 sources。  
如果误走 fallback，或者 sources 数量明显下降，优先看检索和路由。  
如果 route 正常、sources 也正常，但生成内容仍然异常，再怀疑模型输出质量。

### Q2：为什么 `cancelled` 和 `internal_error` 一定要分开？

**答：**

因为 `cancelled` 很多时候是客户端断开，不代表服务端代码坏了。  
如果把它和内部错误混起来，错误率会被误放大，排障方向也会跑偏。

### Q3：为什么 fallback 不一定是 bug？

**答：**

因为并不是所有问题都应该走知识库。  
像打招呼、泛化问题，本来就更适合 fallback。  
真正需要关注的是“知识库应该命中的题却误走 fallback”。

### Q4：如果面试官问“你项目哪里最容易坏”，你怎么答？

**答：**

我会答三类：

1. 多轮 query rewrite 导致的检索偏移
2. 检索节点被安全规则剔除后上下文不足
3. 流式接口在超时、客户端取消和并发冲突下的边界问题

这三个最能体现系统复杂度，也最能体现工程判断。

## 7. 你现在绝对不要吹的点

1. **不要说已经有完整故障平台。**  
   现在主要还是请求级日志 + 业务日志 + 手工排障顺序。

2. **不要说所有失败都已经量化统计。**  
   现在能看、能查，但还没有完整 dashboard。

3. **不要说已经做了自动 root cause 分析。**  
   现在还是工程师通过 request_id 和阶段日志排障。

---

## 8. 最后一句话

一个项目真正成熟起来，靠的不是“功能越来越多”，而是：

**你越来越清楚它会在哪里坏，并且坏了以后不会乱查。**
